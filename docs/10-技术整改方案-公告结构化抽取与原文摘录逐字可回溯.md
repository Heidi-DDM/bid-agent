# 技术整改方案：公告结构化抽取与原文摘录逐字可回溯

> 状态：**方案已评审通过；P0–P3 已实施（2026-09-11，见 04-修改日志同日两条、F004 v1.5/v1.6、F020 v1.17）；P4（LLM 受约束路径）待启用** · 2026-09-11
> 触发案例：河北工业大学室外下水疏通掏挖清淤服务采购项目（二次）公开招标公告——资质要求截断丢子项、联合体极性反转、原文摘录无法回定位。
> 关联规格：F004（公告入库解析）、F005（字段级原文溯源 assertion 逐字）、F021（招标材料解析运行时）。
> 冻结契约提示：F005 §4 "assertion（原文摘录，逐字）" 与 F004 §4 "原文摘录（逐字）" **已是冻结契约**——本方案不是变更契约，而是**落实契约**；新增的偏移字段属 schema 扩展，需按 AGENTS.md 规则 5 走规格变更记录（见 §6）。

## 1. 案例复现（已在当前代码上验证）

以用户提供的公告原文片段直接运行 `runtime/parsing/announcement_prescreen.extract_prescreen`（2026-09-11 实测）：

**问题一：资质要求截断丢子项**

```
原文：投标人应具备建设行政主管部门核发的建筑工程施工总承包三级及以上资质或市政
     公用工程施工总承包三级及以上资质；具有建设行政主管部门颁发的有效期内的安全生产许可证。
抽取值：具备建设行政主管部门核发的建筑工程施工总承包三级及以上资质或市政公用工程
       施工总承包三级及以上资质        ← "；具有…安全生产许可证。" 整段丢失
```

**问题二：联合体极性反转（表单式）**

```
原文：是否接受联合体投标：否
抽取值：接受联合体投标              ← 命中了标签片段"是否【接受联合体投标】：否"，
                                    无视冒号后的值"否"，语义完全反转
```

**问题三：原文摘录定位错误**

- 联合体字段的摘录被抽成 `是否接受联合体投标：否 是否专门面向中小企业：否。`——摘录横跨了下一个字段（表单式公告字段间用空格不用句读，句界扫描找不到终点）；
- 更系统性的是：摘录是在 `_clean_text`（空白折叠）后的文本上重新拼接的字符串（回扩窗口 100 字 + 220/260 截断加"…" + rstrip 标点），**不保证是固化 .txt 原文的逐字子串，也没有任何字符偏移**。用户点开"原文摘录"去公告原页人工对照时，自然对不上位置。

## 2. 根因分析（四个系统性问题）

排查范围：`runtime/parsing/announcement_prescreen.py`、`runtime/parsing/extractor.py`、`runtime/parsing/router.py`、`runtime/collecting/parsers.py`、`runtime/collecting/service.py` + prototype 展示层。**同类缺陷不止这三处，全库共 30+ 处**，完整清单见附录 A。归纳为四类：

### 2.1 句读语义一刀切："；"被当成句界，但它常是同一条款的并列连接符

- prescreen `_SENT_END_CHARS = "。；;"`（announcement_prescreen.py:66）：资质/人员/信用条款里 `资质A或资质B；安全生产许可证` 的"；"分隔的是**并列子条件**，切在第一个"；"就把后面的硬性要求丢了（问题一根因，三处同根：prescreen 短语式分支 :227-230、prescreen 标签式 `_list_aware_tail` :119-147、extractor `qualification_grade` 分支② `资质要求[：:][^；;。]{5,300}` extractor.py:127）；
- 反向问题：`_clause_tail`（:102-107）只认句读不认下一个 label，`_clean_text` 把全文折叠成单行后，`采购人：河北某某大学 建设地点：… 计划工期：…` 一路吞到句号——跨字段吞并。

### 2.2 label-value 表单式公告没有"先定 label 边界、再取冒号后的值"的机制

- 联合体锚点 `(?:接受|不接受)\s*联合体投标`（:164）在"**是否**接受联合体投标：否"里命中标签片段，极性词全丢（问题二根因）；
- 同族问题：`budget_amount` 缺 `[:：]?`（`总投资：5000万元` 不命中）、MAIN_CARD `tenderee` 终止符不含"："（td 粘连时整字段丢失）、`html_to_text` 不给 `</td>` 转行（parsers.py:148，`<td>是否接受联合体投标</td><td>否</td>` 净化成"是否接受联合体投标否"——表单值粘连是极性误读的温床）。

### 2.3 布尔/枚举字段靠"词出现"而不是"值判定"

- 联合体把极性词编进锚点本身，遇到 `是否…：否` / `☑不接受` / `（是/否）接受：否` 三种版式分别产生反转或漏采；extractor 的 consortium 锚点只认"不接受"（:201），公告写"接受联合体"时反而漏报进 missing 复核队列；
- 同族：extractor `project_type` 过滤逻辑（:467）把合法的"货物/服务"值反转为缺失。

### 2.4 摘录（assertion）全程无偏移、五层重拼——"逐字"契约事实上从未被机器保证

```
html → html_to_text(空白折叠/标签转行) → _clean_text(再折叠) → 正则命中
     → _clause_snip(回扩100字/截断220加"…"/rstrip) → 前端再 slice(0,300)
```

- 每层都可能破坏"逐字子串"性质，且 `detail_summary` 落库（service.py:400）只有字符串、无 `(start, end)` 偏移、不与固化文本的 `content_hash` 关联——**F005 冻结的"assertion 逐字"从未被校验过，这是问题三的结构性根因**；
- `router.ParsedPage` 只有 `page_no + paragraphs`，无字符偏移，招标文件侧（F021）同病；
- 两套归一化口径并存：extractor 匹配前全去空白、prescreen 只折叠不去除——`投标截止时间为 2026 年 10 月 10 日`（数字与汉字间空格）在公告侧直接漏采。

## 3. 目标定义："百分百准确"的可验收口径

"100% 准确"不可能靠无限加正则实现，业界共识（见 §4 调研）是把它拆成**可机器验证的不变量**——凡不满足者**降级为待补/人工复核，绝不静默给出错误值**（与 AGENTS.md 规则 1"数据缺失默认阻断"同构）：

| # | 不变量 | 机器可验证 |
|---|---|---|
| G1 | 每个展示值必须携带原文逐字摘录 quote，且 `固化文本[start:end] == quote`（round-trip 校验） | ✅ 一次字符串比较 |
| G2 | 布尔/枚举字段（联合体等）的值必须由确定性规则**从 quote 派生**（`值 = f(quote)`），quote 缺失即 blocked，不允许"无摘录的极性" | ✅ 极性词表 + 断言 |
| G3 | 多子项条款（"；"并列）不允许静默截断：值要么覆盖完整条款组，要么截断处显式标 `truncated` 并降 confidence 进人工复核 | ✅ 截断标记检查 |
| G4 | 未命中/校验不过 → `missing / review` 占位进待补队列，**绝不推断填充** | ✅ 已有契约 |
| G5 | 前端点击摘录能在固化原文视图中**按偏移高亮定位**，定位失败（偏移失效，如文本版本变化）时按 content_hash 判定并隐藏定位按钮，不让用户看到错位 | ✅ E2E 断言 |

验收基准：以"河北工业大学（二次）"为首期 golden 案例，**极性字段 0 反转、资质条款 0 静默截断、摘录 round-trip 通过率 100%**，并进入回归测试防复发。

## 5. 整改方案（分五步，规则确定性优先，LLM 只做受约束增强）

### P0 — 三个案例 bug 的确定性修复（最小改动，当天级）

> **已实施（2026-09-11）**。实施中两点实测修正：① 河北工大真实公告的联合体写法是政采表单 **「本项目（是/否）接受联合体投标： 0」**（0=否、1=是），已纳入表单式判定；② `html_to_text` 末尾 `_WS` 把所有换行折叠为空格，固化 .txt 实为**单行**（附录 A parsers #2 原描述"含 \n\n"不准确，已更正）——P1 偏移映射因此只需处理"块边界→空格"一种变换。联合体值本期为归一短语（不接受/接受联合体投标），枚举化随 P2。

改 `announcement_prescreen.py`，不动契约：

1. **资质条款"；"并列不切断**：`qualification` 短语式/标签式取值改为"扩到条款组终点"——终点 = 下一个**条款编号**（`_RE_CLAUSE_NUM`）或下一个**已知 label**（`资质要求|业绩要求|项目经理|…[：:]`）或"。"+换行，而非第一个"；"。首次落地即把"安全生产许可证"并入值；
2. **联合体 label-value + 极性归一**：
   - 锚点优先级：① 表单式 `是否接受(?:联合体)?投标?[：:]\s*(是|否)`（取值为 true/false）；② 勾选式 `[☑√]?\s*(接受|不接受)\s*联合体`；③ 叙述式 `(?:接受|不接受)联合体投标`。**极性词必须出现在 quote 内且位于标签冒号之后**，命中标签片段（如"是否"后的"接受"）一律不采；
   - 输出归一为枚举 `accepts_consortium: true/false` + quote，展示层只渲染枚举值；
3. **摘录句界修复**：`_clause_snip`/`_clause_tail` 终点条件增加"下一个已知 label 起点"，表单式公告不再横跨相邻字段；
4. `html_to_text` 的 `_RE_BLOCK` 增补 `td|th` 转行（或单元格间补"："），表单值不再粘连（parsers.py:148）。

同步修 extractor.py 两处同根问题：`qualification_grade` 分支② `[^；;。]{5,300}` 的"；"截断；`consortium` 锚点补"接受"写法（漏报型反转）。

### P1 — 偏移保持管线（offset-preserving pipeline）——G1/G5 的骨架

> **已实施（2026-09-11）**，与原稿的三点偏差如实登记：① 抽取工作面**保留折叠文本**（未把 `_clean_text` 去掉）——改为 `_collapse_with_map` 建"折叠位置→固化原文位置"映射，值与偏移同源，回归风险最小（全锚点语义不变）；固化 .txt 本就是 `html_to_text` 输出，quote 直接切自固化原文；② 兜底重定位**未引入 RapidFuzz**（仓库慎引库），改为"原文精确 → 折叠重定位（构造性精确）→ 找不到即放弃"，无模糊阈值、无错位风险；③ `queue.html`（招标文件规则候选）只去掉了展示端二次截断，**定位待 F021 侧 ParsedPage 偏移化**后再做（当前 extractor 摘录无字符偏移）。存量 8 条候选已用新口径重算；活服务端到端：河北工大 6 个带偏移字段在 API 返回原文上 round-trip 全过。

**原则（借 spaCy/`re.finditer` 惯用法）：值与偏移同源产生，摘录是原文切片而不是重拼字符串。**

1. `html_to_text` 改造为返回 `(净化文本, 偏移映射表)`：净化时逐字符记录"净化位置 → 固化 .txt 原文位置"（映射表可用 run-length 压缩；净化本身不再二次折叠，收敛 §2.4 的五层重拼为两层：html→净化文本（唯一抽取工作面），固化 .txt 即净化文本本身）；
2. `extract_prescreen` 全部锚点改用 `pat.finditer`：每个字段产出 `{value, quote, start, end}`，quote ≡ `净化文本[start:end]`（构造即成立，免校验），再经映射表换算回固化原文偏移；
3. `detail_summary` schema 扩展（**需 F004/F005 变更记录，见 §6**）：每字段增加 `quote`（逐字切片）、`start`/`end`（固化文本偏移）、`content_hash`（绑定固化版本，文本重抓/版本变化即判定偏移失效）；
4. **round-trip 硬校验入库门禁**（借 TDS/MDPI 实践）：落库前断言 `固化文本[start:end] == quote`；不过者**该字段降级 missing/review 转人工**，绝不带病入库——审计关键字段（资质/联合体/金额/截止时间）零容忍，其余字段记录告警；
5. 前端（import.html 候选详情、queue.html 规则候选）："原文摘录"从纯文本 `<details>` 升级为**点击→原文视图打开并按 (start,end) 高亮滚动**；偏移失效（content_hash 不匹配）时用 RapidFuzz `partial_ratio_alignment`（阈值 ≥95）兜底重定位，仍失败则隐藏定位按钮并提示"请回原页核实"——**宁可不定位，不错位**。

### P2 — 极性与枚举防反转层——G2

> **已实施（2026-09-11）**：`POLARITY_FIELDS` 注册表（P0 的联合体判定收编 + 新增 `sme_dedicated` 是否专门面向中小企业），每字段 `enum` 机器可校验（golden 0 反转红线）；`project_type` 优先级分类器落地（prescreen 标题 + extractor 主卡共用，另补「施工图设计 > 施工」防抢类）；联合体值仍为归一短语（展示口径不变），枚举入 `enum` 字段——方案原稿的"值直接改布尔枚举"调整为"短语 + enum 并存"，避免前端/存量数据破坏。

1. 建"极性字段注册表"：`joint_venture/accepts_consortium`、`是否专门面向中小企业`、`project_type`（工程/货物/服务）等，每个字段声明：判定函数 `f(quote) -> 枚举值`、极性词表（接受/不接受、是/否、☑/□/√/＊）、无法判定时输出 `undetermined`；
2. **值一律由 quote 派生**（LLM 或正则都只负责产出 quote，不直接产出极性），quote 内极性词缺失/冲突 → blocked 进待补；
3. `project_type` 由标题分类器按 施工>EPC>设计>监理>货物>服务 优先级判定，替换现在的首命中 + 包含性过滤（修掉"货物/服务反转为缺失"）。

### P3 — golden 回归体系（防复发，本案例直接进语料）——G3/G4 的度量

> **已实施（2026-09-11，第一批）**：语料落在 `runtime/tests/golden/announcements/`（6 案 34 例：河北工大（二次）/惠招标太行冷链/唐山三友 EPC/询比采购/联合体极性矩阵 13 变体/快赢锚点 17 变体），body 带 sha256 锁定；断言三层不变量（关键子项包含 / quote round-trip / 极性 enum）；CI 门禁=pytest 全量（golden 不过即红，等价 fail-under=1.0）。附录 A 快赢批次同日修复：预算金额（政采 元/亿元）、工期（为/约/个月）、时间空格、地区止于市、特级、标段"划分为"、条款号误捕日期、（是/否）联合体词表。**未在本批的附录 A 项**（发布日期冒充、docx/OCR 结构、extractor MAIN_CARD lookahead/region、publish_date URL guard 等）按"人工复核修正回流→新增 golden→修复"机制继续闭环。

> **边界澄清（2026-09-11 评审问询）**：golden 是**离线 CI 回归**，只在改代码时运行，**不参与线上对新公告的抽取**。新说法的路径是：运行时规则未命中 → 待补/人工复核 → 修正回流 → 该说法新增为考题——考卷挡的是"改坏的代码"，不挡新公告，只增不减。

照抄 tender-extract 的评测骨架，落到本仓库 pytest 体系（已有 `runtime/tests/test_announcement_prescreen.py`、`test_parsing_extractor.py` 扩展即可）：

1. `tests/golden/announcements/`：每案例一个 JSON（输入正文 + 期望字段值 + 期望 quote + 期望偏移区间），**首期收录：河北工业大学（二次）本案例、农大基线、唐山三友 EPC、勾选式/表单式/叙述式联合体各一**；语料记录来源 URL + SHA256（锁定可复现，符合合规台账口径）；
2. 断言三层（**不变量式，非逐字对答案**——将来主动优化取值边界，只要不变量不破即不误报）：① 关键子项必须包含（如资质值须含"安全生产许可证"）；② quote 为固化文本逐字子串（round-trip）；③ 极性字段枚举正确（0 反转红线）；
3. CI 门禁：`pytest runtime/tests -k golden --assert-fail-under=1.0`（golden 集 100% 通过才绿，低于阈值挡合并——对应 tender-extract `--fail-under 0.95`，我们取 1.0 因 golden 集小而精）；
4. 人工复核修正回流：复核人修正的值/摘录写回 golden（对齐 F021 `revised_payload` 复核流），语料随真实公告持续扩充；
5. 附录 A 的 30+ 处缺陷按此逐条转成 golden 反例再修复（防止只修用户报告的三处）。

### P4 — LLM 受约束增强路径（可选，规则覆盖率不足时启用）

对齐 F021"模型可用时增强 clause 语义层"的既定设计与 tender-extract"规则优先、LLM 兜底"分层：

1. 规则层置信度低/冲突/missing 的字段才调 LLM（instructor + pydantic 契约：`{field_key, quote, start_hint}`，**只准输出 verbatim quote 与字段名，不准直接输出值**）；
2. LLM 返回后走与规则层完全相同的校验链：`normalize(quote) in normalize(原文)`（借 TDS 口径：归一只折叠空白，不改写汉字）+ 偏移回定位（diff-match-patch/ RapidFuzz）+ `值 = f(quote)` 派生；
3. 校验不过 → 重试一次 → 仍不过转人工（对齐 F021 review 流），**审计关键字段永不由 LLM 直接定值**。

## 附录 B：本方案的"100%"边界声明

- 本方案保证的是：**展示的每一个值要么带可机器校验的逐字摘录与偏移，要么显式 missing/待复核**——错误值零容忍、缺失零掩盖；
- 不能保证的是：正则/规则层对全平台公告版式的覆盖率 100%（这正是 P3 golden 持续扩充与 P4 LLM 兜底要收敛的对象）；覆盖不到的版式会以 missing/复核形态出现，**由人工复核兜底**（F021 已有 review 流），符合"禁止编造、数据缺失默认阻断"红线。

## 附录 C：评审预答疑问（2026-09-11，动手前确认）

**Q1 考试卷用案例当"死规则"，公告说法变了会不会牵制输出？**
不会。golden 是离线 CI 回归，只在改代码时运行，与线上新公告抽取零接触（见 P3 边界澄清）。新说法走"运行时未命中 → 待补/人工 → 修正回流 → 新增考题"，考卷只增不减；断言写成不变量（含关键子项 / quote 逐字 / 极性枚举）而非逐字对答案，主动优化措辞不会误报。

**Q2 坐标回检会不会被采集限频（如 30s/次）卡住报错？**
不会。限频只作用于"抓公告详情页"的 HTTP 请求（`COLLECTION_POLICY.enforce_rate_limit`）；round-trip 回检是同进程内存字符串比对（`固化文本[start:end] == quote`），零网络；前端定位读的是对象库本地 .txt + 本地偏移，RapidFuzz 兜底亦为纯本地计算。全链路唯一触网的是导入时那一次抓取，与现状一致。

**Q3 "要么对、要么明说不知道"会不会导致输出全为待补？**
不会。① 新管线的 quote 由原文按偏移切片构造，回检按构造必过——它防 bug，不筛结果，抽取成功的字段不因回检减少；② 现有规则已抽出多数字段（本案例是截断/反转而非空抽），P0 后继续保留且更完整；③ 新增待补只来自"以前抽错却装作抽到"的字段（错值转待补正是目的）。并以 §7 第 5 条护栏指标（待补率不高于改造前基线）在验收上硬性防止一刀切实现。
