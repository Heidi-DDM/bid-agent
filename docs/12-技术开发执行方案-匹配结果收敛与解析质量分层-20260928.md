# 技术开发执行方案：匹配结果收敛与解析质量分层

- **版本**：v0.2（阶段 0-3 已实施，2026-09-28；阶段 4 验收与业务签字开放——见 §13）
- **日期**：2026-09-28
- **适用范围**：招标文件解析完成后的规则、匹配、风险页、评分页、处置队列和准入结果
- **关联决策**：ADR-001、ADR-004、ADR-007、[ADR-008](06-产品决策记录/ADR-008-资格准入评分分析与投标执行分层.md)
- **关联规格**：F008、F020、F021、F023、F024
- **变更性质**：涉及冻结的状态、结果口径和 API 时，须先完成 ADR-008 评审，并按本方案更新对应功能规格、迁移、契约测试后实施；本文件本身不改变线上行为。

## 1. 背景、走查结论与目标

### 1.1 已完成的体验走查

以投标专员账号走查了本机原型的“搜索与推送 → 项目工作台 → 上传/解析 → 自动匹配 → 风险与缺失 → 待确认与处置”链路，并查看了硬性要求、评分项、动作项和匹配详情。当前“隐藏解析、直达匹配”的主方向正确，但结果页仍存在信息层级、判定精度和生命周期语义混杂的问题。

### 1.2 明确排除项：历史文件测试样本

当前没有与待选项目一一对应的可用招标文件，团队以企业已完成项目的招标文件进行脱敏解析验证。因此页面所见项目和招标文件在名称、采购人或地点上的差异，**不是本轮待修复的“串档缺陷”**。

本方案不修改也不放松 ADR-004 的生产文件—项目身份校验。测试环境只需把该材料显著标注为“历史解析样本／非当前项目文件”，并禁止把其匹配结果作为真实项目准入、审批或递交依据；生产模式仍按既有身份门禁处理真实文件关联。

### 1.3 要解决的问题

| 编号 | 走查发现 | 业务风险 | 本轮目标 |
|---|---|---|---|
| O1 | 解析未定位/不确定条目位于匹配页顶部，且与企业缺证混在一起 | 用户将模型质量问题误读为企业资格风险 | 独立解析质量域，首屏只显示简洁摘要与高风险例外入口 |
| O2 | 硬性、评分、动作在同一矩阵/缺证队列中处理 | 未开始递交、开标或踏勘被误判为企业资料不全 | 资格、评分、执行计划、解析质量四域分层 |
| O3 | “安全员 C 证有效数量 0，不足 3 或证据缺失”合并两个事实 | 明确不满足与资料未核验无法采取不同动作 | 结论原因码和状态拆分 |
| O4 | 项目经理资格、B 证、在施等可能引用不同人员 | 形成不存在的“拼接式满足” | 候选班子/岗位绑定与同一 `person_id` 约束 |
| O5 | 评分页把评标方法说明当作评分项，出现“可复算 0/0、未满分” | 用户误以为企业失分，或误解系统可算报价 | 评分规则分类、可计算性和输入边界 |
| O6 | 同一企业缺证被多个条款重复列出 | 待办膨胀、责任不清 | 证据缺口任务聚合，仍保留逐条回链 |
| O7 | 矩阵、待确认页可能呈现不同的确认/复核状态 | 用户不知道哪个结论是当前版本 | 统一运行快照、版本标识和 stale 机制 |

### 1.4 成功标准

1. 用户在结果首屏能在 10 秒内识别“明确不满足、待补资料、人工复核”三类优先事项，而不会把解析质量或未开始动作误读为企业缺证。
2. 任一“满足”结论可回链至招标条款、企业证据和同一人员/班子方案；不能回链则不得进入 `satisfied`。
3. 系统不会因“有 0 条已核验证据”和“没有可核验资料”输出同一个事实结论。
4. 没有可计算评分项时，不显示“得分 0/0”或“未满分”；应如实说明无法自动计算的原因。
5. 任意文件、规则、企业证据、人员可用性、解析处置改变后，当前结果可识别为 `stale`，并能重放到同一输入快照。
6. 现有红线不变：不推断满足；满分不自动投标；模型/向量分数不进入准入公式；结果有条款和证据回链。

## 2. 产品信息架构与页面行为

### 2.1 目标信息架构

```text
项目工作台
├─ 当前结论（资格与资源）                ← 默认页/首屏
│  ├─ 结论摘要、版本、判定时点、历史样本标识
│  ├─ 优先处理（最多 3 项）
│  └─ 硬性要求矩阵与证据详情
├─ 评分分析
│  ├─ 可自动计算的客观项
│  ├─ 待内部质量评审项
│  ├─ 报价公式（只读规则 + 授权输入）
│  └─ 评标方法说明/待结构化规则
├─ 投标执行计划
│  └─ 按 preparation / approval / submission / opened 阶段的任务、责任人、截止和回执
├─ 解析质量与待确认项
│  └─ 未定位、低置信、冲突、未结构化候选及处置审计
└─ 原文、规则、证据与运行历史
```

页面不是把内容“藏掉”，而是根据用户当下决策分层。解析质量仍保持可见、可处理和审计，且依 ADR-007 继续阻断满分；它不再以一长串“未定位”抢占资格结论首屏。

### 2.2 当前结论页（原 `matrix.html`）

1. 顶部固定显示：项目/标段、`run_id`、规则版本、企业资料快照、文件集合版本、`as_of`、生成时间和新鲜度；历史测试材料显示醒目但非错误态的“历史解析样本／非当前项目文件”标识，并附“不可用于真实审批或递交”。
2. 摘要卡仅显示四类可行动数量：明确不满足、待补资料、人工复核、已满足；状态排序固定为：明确不满足 → 待补资料 → 人工复核 → 已满足。首屏“优先处理”最多显示 3 项，余项进入“查看全部”。
3. 新增“解析质量：`n` 项待处置”的次级提示；没有硬性未定位时采用中性样式，点击打开抽屉。若有会影响准入的硬性解析例外，摘要说明“满分准入暂不可用”，但不把它计为企业缺证。
4. 硬性矩阵的每行展示：结论标签、原因码、实际值/要求值、证据状态、关联人员方案（如适用）、条款页码和下一步。`not_satisfied` 与 `blocked_missing_data` 必须视觉和文字不同。
5. 删除浏览器 `prompt()` 处置方式。改为模态表单：决策（通过/本文件无此条款/转深度复核）、必填理由、检索词或检索范围、可选页码、附件/备注；提交显示 `request_id`，取消/Escape 不写入。

### 2.3 评分分析页（原 `score.html`）

评分项按 `score_classification` 分组，不再仅按“评分项”平铺：

| 分类 | 页面文案 | 系统行为 |
|---|---|---|
| `objective_calculable` | 可自动复算的客观项 | 显示公式、输入、证据、得分/满分和差距 |
| `subjective_review` | 待内部质量评审 | 显示评审状态/依据，不显示虚构的评委分数 |
| `price_formula` | 报价计算规则 | 显示原文公式和授权输入版本；无输入即“待授权输入”，绝不推荐报价 |
| `methodology_only` | 评标方法说明 | 仅归档解释，不计入可复算总分 |
| `unstructured` | 评分规则待结构化 | 展示原文、定位和待办；结论为不可计算 |

摘要替换为：“可自动计算 X 项”“待内部评审 Y 项”“待结构化 Z 项”。若 X=0，明确显示“当前无可自动计算评分项，不能自动判断是否达到内部满分”，而不是 `0/0` 或“未满分”。

### 2.4 投标执行计划页

将动作项从资格矩阵和补证队列迁出，按时间线显示报名、CA、保证金、编制、递交、开标、踏勘等。每项有责任角色、责任人、绝对截止时点、依赖、状态和回执。只有原文显式要求且规则标注 `required_by_stage=approval_ready` 的动作才会出现在审批前门禁；其余按后续阶段检查。

### 2.5 解析质量与待确认页

解析质量按风险而非“所有常见字段探针”排序：

1. 已定位但条款冲突/版本冲突；
2. 原文应存在的关键章节或强锚点未定位；
3. 模型定位、低置信候选；
4. 常见探针未命中但无明确原文预期。

最后一类须标为“未检出，不代表文件不存在该要求”，不允许直接生成企业匹配失败。队列中显示 `parse_exception_id`、规则/候选版本、定位页码、检索词、风险依据、处置历史。处置完毕后沿用 ADR-007 生成新规则快照并使旧匹配结果 stale。

## 3. 目标领域模型与状态模型

### 3.1 Requirement 的领域边界

保留既有 `hard_requirement`、`scored_requirement`、`action_requirement`，新增或明确下列字段（JSON 快照与关系表均需保存）：

| 字段 | 适用对象 | 说明 |
|---|---|---|
| `domain` | 全部 | `qualification` / `scoring` / `operation`；与 `req_type` 交叉校验，不能由前端猜测 |
| `decision_scope` | 硬性/评分 | `admission` / `information_only`；只有前者进入内部准入 |
| `score_classification` | 评分 | 见 §2.3 枚举；`methodology_only` 不计分 |
| `comparison_status` | 硬性/评分 | `comparable` / `missing_rule_params` / `needs_professional_judgement` / `not_applicable` |
| `person_binding_policy` | 人员相关 | `none` / `same_person_required` / `same_team_required` / `alternative_candidates_allowed` |
| `role_code` / `role_count` | 人员相关 | 例如 `project_manager`、`safety_officer`；不能仅靠文本匹配职位 |
| `task_kind` | 动作 | `registration` / `bond` / `submission` / `opening` / `site_visit` 等受控枚举 |
| `required_by_stage` | 动作 | `preparation` / `approval_ready` / `submission_ready` / `submitted` / `opened` |

`requirement_id`、`clause_ref`、`source_version_refs`、`as_of` 和原文断言仍为必填回链；不得从模型猜测参数、人员关系或时点。

### 3.2 匹配项的结论、原因与事实值

为避免“0 或缺证据”混淆，`match_items` 增加结构化字段：

```json
{
  "result": "not_satisfied",
  "reason_code": "verified_quantity_insufficient",
  "required_value": {"operator": ">=", "value": 3, "unit": "person"},
  "observed_value": {"value": 0, "source": "verified_enterprise_snapshot"},
  "evidence_state": "sufficient_but_insufficient",
  "evidence_refs": ["EV-..."],
  "candidate_plan_id": "CP-...",
  "next_action": "replace_or_add_qualified_person"
}
```

最小原因码表：

| 结论 | `reason_code` 示例 | 处置 |
|---|---|---|
| `not_satisfied` | `verified_quantity_insufficient`、`grade_below_requirement`、`certificate_expired`、`profession_mismatch`、`onsite_conflict` | 更换/补足资源，不能用“补一份证明”掩盖事实 |
| `blocked_missing_data` | `enterprise_record_missing`、`evidence_missing`、`evidence_pending_verification`、`validity_date_missing` | 创建或合并补证任务 |
| `manual_review` | `evidence_conflict`、`rule_unstructured`、`candidate_plan_unselected`、`professional_judgement_required` | 指派具备权限的复核人 |
| `not_calculable` | `formula_missing`、`authorized_input_missing`、`scoring_evidence_missing` | 评分规则/授权输入/证据处置 |
| `parse_exception` | `anchor_not_located`、`llm_candidate_pending`、`source_conflict` | 解析质量处置，非补证 |

不得用 `unverifiable` 作为前端唯一显示词。为兼容历史数据可保留数据库枚举，在投影层映射到以上更细状态及原因码；无可靠映射的历史行显示“历史结果，需重算确认”。

### 3.3 候选人员与拟派班子

新增不可变快照实体：

| 实体 | 核心字段 | 用途 |
|---|---|---|
| `candidate_plans` | `candidate_plan_id`、`run_id`、`lot_id`、`status`、`selection_basis`、`created_at` | 一次匹配运行中的候选班子方案 |
| `candidate_plan_members` | `candidate_plan_id`、`role_code`、`person_id`、`is_primary`、`availability_as_of`、`evidence_refs[]` | 岗位和同一人员的绑定 |
| `candidate_plan_requirement_links` | `candidate_plan_id`、`requirement_id`、`person_id`、`result`、`reason_code` | 说明某项由谁、以什么证据判断 |

算法顺序：先按岗位硬约束和 `as_of` 筛掉无效候选，再以同一 `person_id` 聚合项目经理相关条件，生成每个候选方案的完整矩阵，最后选择/展示候选方案。若没有任何完整方案，输出 `manual_review` 或明确不满足，不得跨方案拼接。候选排序只能使用已配置、可审计的确定性优先级（例如证据完整度、有效期覆盖），不得使用大模型偏好或向量相似度决定满足。

### 3.4 解析例外、补证任务与执行任务

新增/规范三种分离对象：

| 对象 | 主键及关联 | 可影响什么 | 不能影响什么 |
|---|---|---|---|
| `parse_exceptions` | `parse_exception_id`、候选/材料/解析版本 | 解析质量、ADR-007 满分阻断 | 直接宣告企业不满足 |
| `remediation_tasks` | `task_id`、`gap_key`、`requirement_refs[]`、`evidence_need` | 补证/核验待办 | 替代明确不满足的资源决策 |
| `operation_tasks` | `operation_task_id`、`action_requirement_id`、阶段/截止/回执 | 投标执行就绪 | 资格/评分结论 |

补证任务的稳定聚合键建议为：`enterprise_scope + lot_id + missing_fact_type + evidence_requirement_fingerprint + as_of_bucket`。后端创建时以此 upsert，更新 `requirement_refs[]`，保留每一个条款和原因；不要以 UI 文案作键。不同主体、不同标段、不同有效时点、不同证据法定要求不得错误合并。

### 3.5 运行快照、新鲜度与一致性

每个 `MatchRun` 必须固化并由所有投影接口原样返回：

```text
run_id
project_identity_version          document_set_version
ruleset_version                   parse_exception_snapshot_version
enterprise_snapshot_version       personnel_availability_snapshot_version
candidate_plan_snapshot_version   retrieval_run_id
as_of                             matcher_version
```

任何一个输入变化（文件/澄清、解析处置、规则参数、企业证据状态、人员在施或有效期、候选方案确认、授权评分输入）均创建新版本并将受影响运行标为 `stale`。前端不得分别向“矩阵”“待确认”“队列”取不同运行的无版本数据：所有接口接受可选 `run_id`，默认仅返回最新 `current` 运行，并在响应中回显同一 `run_context`。

## 4. 后端实现与 API 契约

### 4.1 实施原则

- 服务端拥有分类、状态迁移、准入和权限判断，前端仅投影；禁止用隐藏按钮代替门禁。
- 写接口都需要角色、项目状态、输入版本、`Idempotency-Key`、审计事件和 `request_id`；所有列表读取须按项目/标段/权限过滤。
- 所有接口只允许引用已锁定的版本；若版本不再 current，应返回 `409 stale_input`，而不是悄悄覆写当前结果。
- 响应中的文本由服务端字典映射/前端国际化层生成，判定使用稳定枚举和原因码。

### 4.2 推荐接口（目标态；需先纳入 F020）

| 接口 | 方法 | 角色 | 关键输入/输出 | 说明 |
|---|---|---|---|---|
| `/api/v1/projects/{id}/result-overview` | GET | 项目可见角色 | `run_id?` → `run_context`、资格摘要、解析质量摘要、优先事项 | 结果首屏的单一读取源 |
| `/api/v1/projects/{id}/qualification-matrix` | GET | 项目可见角色 | `run_id?`、`lot_id?`、分页/状态筛选 | 只返回资格与资源项 |
| `/api/v1/projects/{id}/scoring-analysis` | GET | 投标/经营角色 | `run_id?` | 按评分分类投影，不生成报价 |
| `/api/v1/projects/{id}/operation-plan` | GET | 投标执行角色 | `run_id?`、`stage?` | 独立动作计划与执行门禁 |
| `/api/v1/projects/{id}/parse-exceptions` | GET | 投标/复核角色 | `parse_version?`、筛选 | 解析质量的唯一队列源 |
| `/api/v1/parse-exceptions/{id}/decisions` | POST | 投标专员/复核人 | `decision`、`reason`、`search_scope`、`page_refs[]`、`version` | 代替浏览器 prompt；触发规则/运行 stale 链 |
| `/api/v1/projects/{id}/candidate-plans` | GET | 项目可见角色 | `run_id?` | 返回候选班子和人员—条款回链 |
| `/api/v1/projects/{id}/candidate-plans/select` | POST | 投标负责人 | `candidate_plan_id`、`run_id`、理由 | 如业务需要人工选定方案，生成新快照并重算 |
| `/api/v1/projects/{id}/remediation-tasks` | GET | 资料/投标角色 | `run_id?` | 按聚合缺口返回任务和覆盖条款 |
| `/api/v1/operation-tasks/{id}` | PATCH/POST | 任务责任人 | 状态、回执、版本 | 仅更新动作计划，按阶段验证 |

旧接口 `GET /matrix`、`GET /queues`、`GET /admission` 过渡期间不直接删除：增加 `run_context` 与 `deprecated_projection`，先由新接口承接页面；旧载荷继续可读但不承诺新增字段完整性。审批创建接口必须继续以服务端 `internal_admission_eligible=true`、结果 current 和非历史样本为前提。

### 4.3 匹配编排调整

将现有“解析完成 → 匹配”拆为稳定流水线：

```text
parse.completed
  → 自动确认 + parse exception snapshot
  → ruleset snapshot（可带 pending exceptions）
  → build enterprise/personnel snapshot
  → classify requirements
  → generate candidate plans（人员相关项）
  → diagnostic match（资格 / 评分 / 动作分别执行）
  → build aggregated remediation tasks + operation tasks
  → calculate four domain summaries
  → admission gate + persist run context
  → publish match.completed(run_id)
```

关键规则：

1. `parse_exception` 使 `internal_admission_eligible=false` 的原因必须明确为 `parse_exceptions_pending`，不能落入 `blocked_missing_data`。
2. `action_requirement` 仅产出 `operation_tasks`；除 `approval_ready` 且明确配置的动作外，不参与资格和满分门禁。
3. `methodology_only` 不参与 `total_score/max_total_score`；`unstructured` 使评分结果为 `not_calculable` 或 `manual_review`，不得虚构 0 分。
4. 资料缺失才创建 `remediation_task`；明确数量不足、证书过期或在施冲突创建“资源处置建议”，不能写成“补一份缺失证据即可通过”。
5. 匹配运行的幂等键至少含项目、标段、文件集合、规则、企业/人员快照、解析例外快照、授权评分输入及引擎版本。相同输入复用结果；任一输入不同创建新运行。

### 4.4 准入汇总伪代码

```python
qualification_ok = all(
    item.result == "satisfied"
    for item in qualification_items
    if item.decision_scope == "admission"
)

scoring_ready = (
    no_required_score_item_is("not_calculable", "manual_review")
    and all_required_objective_items_reach_configured_policy()
    and subjective_items_pass_internal_review()
)

parse_ready = parse_exception_summary.blocking_count == 0
approval_actions_ready = all(
    task.status in {"ready", "completed"}
    for task in operation_tasks
    if task.required_by_stage == "approval_ready"
)

internal_admission_eligible = (
    qualification_ok and scoring_ready and parse_ready and approval_actions_ready
    and run.is_current and not project.is_historical_sample_context
)
```

其中 `is_historical_sample_context` 是测试隔离标识而非企业资格结论。正式环境的项目身份校验继续在匹配和审批入口前执行；不因本方案而跳过。

## 5. 数据库迁移、兼容与回填

### 5.1 迁移顺序

1. **扩展表结构（向后兼容）**：新增枚举/原因码、`run_context` 字段、候选班子、解析例外、动作任务与任务聚合字段；不改写旧 `match_items`。
2. **双写阶段**：新引擎在写旧 `MatchItem` 的同时写新域投影/快照。读取端以 feature flag `MATCH_RESULT_LAYERING_V1` 决定读新旧投影。
3. **回填和审计**：历史运行只做保守分类。无法根据结构化数据区分“明确不满足”与“证据缺失”的，写 `legacy_ambiguous`/`manual_review`，不猜测、不自动产生准入。
4. **灰度读切换**：先对测试项目和脱敏黄金样本开启新页面，核验双写一致性后再扩大；旧接口至少保留一个发布周期。
5. **收口**：冻结旧投影写入、迁移消费者、删除已过期的前端分支前，完成可回滚演练和数据保留核对。

### 5.2 建议迁移/索引

- `match_items`：`domain`、`reason_code`、`evidence_state`、`observed_value`、`required_value`、`candidate_plan_id`、`run_context_version`；索引 `(run_id, domain, match_result)`、`(candidate_plan_id)`。
- `requirements`：`decision_scope`、`score_classification`、`comparison_status`、`person_binding_policy`、`role_code`、`task_kind`；对受控枚举建 CHECK 或应用层严格校验。
- `remediation_tasks`：`gap_key`、`requirement_refs`、`clause_refs`、`status`、`source_run_id`；唯一索引 `(project_id, lot_id, gap_key, status_active)`。
- 新建 `candidate_plans`、`candidate_plan_members`、`candidate_plan_requirement_links`、`parse_exceptions`、`operation_tasks`，全部关联 run/版本且禁止覆盖历史快照。
- 扩展 `admission_results` 为按域保存 `qualification_summary`、`scoring_summary`、`operation_summary`、`parse_quality_summary` 和明确的 `blocking_reasons[]`。

迁移文件只可新增，不得修改已经部署的 Alembic revision；生产迁移必须包含升级、降级（可行部分）和大表索引的锁表评估。

## 8. 测试与验收计划

### 8.1 单元和契约测试

1. **状态拆分**：0 条已核验证据 → `not_satisfied/verified_quantity_insufficient`；无台账/无证据 → `blocked_missing_data/evidence_missing`；过期、专业不符、在施冲突各自有独立原因码。
2. **人员绑定**：A 有项目经理资格、B 有 B 证、C 无在施时，不能输出同一项目经理 `satisfied`；同一人全条件满足时可满足；多个候选方案互不串证据。
3. **评分分类**：综合评估法/随机平均价/百分制为 `methodology_only`；无授权报价不计算报价；主观项未评审不填分；无客观项不输出 0/0。
4. **动作分层**：`submission_ready` 的未开始递交不创建缺证任务、不阻断审批；`approval_ready` 的明确动作未就绪应阻断审批并标明动作原因。
5. **解析例外**：未定位硬性候选只产生 `parse_exception` 并阻断满分；处置为不适用必须有理由和检索范围；最后一项处置后生成新规则快照并使旧 run stale。
6. **任务聚合**：两个条款引用同一缺失信用报告时只产生一个补证任务，任务中列出两个 `requirement_id/clause_ref`；不同标段/时点不合并。
7. **版本和幂等**：相同输入不创建新 run；任一快照版本变化产生新 run；旧 run 不能通过审批；所有读接口的 `run_context` 一致。
8. **权限**：无权角色不能处理解析例外、选班子、录报价、完成他人执行任务；历史样本上下文无法创建审批/递交包。

### 8.2 集成与浏览器验收场景

| 用例 | 准备 | 期望结果 |
|---|---|---|
| A1 解析质量不抢占首屏 | 有 3 个解析例外和 1 个企业缺证 | 首屏优先展示企业缺证；解析质量只有摘要/入口，且准入阻断理由可查 |
| A2 资格结论精细化 | 安全员要求 3 人，已核验 0 人 | 明确“不足 3 人”，显示 0/3 与资源处置建议，不显示“或证据缺失” |
| A3 真缺资料 | 无财务报告记录 | 显示待补资料、创建可回链补证任务，不称“明确不满足” |
| A4 人员不拼接 | 多个人分别满足项目经理子条件 | 没有完整候选方案，不得满足；展示候选缺口 |
| A5 评分说明 | 仅解析出评标方法说明 | “可自动计算 0 项；规则待结构化/方法说明 n 项”，无 0/0 |
| A6 动作尚未开始 | 尚未到递交时间 | 进入执行计划 `not_started`，不进入资格缺证和审批门禁（除非显式 `approval_ready`） |

| A8 历史样本 | 使用脱敏历史招标文件 | 显示历史样本标签；解析/匹配可用于测试，审批与递交入口被拒绝 |

## 10. 风险、缓解和不做项

| 风险 | 缓解 |
|---|---|
| 历史 `unverifiable` 无法可靠回填为更细状态 | 保守标为历史歧义/人工复核，仅新 run 使用细粒度状态 |
| 候选方案组合数膨胀 | 先用岗位硬过滤、限定展示 Top-N、设置确定性排序和超时降级人工复核 |
| 动作迁出资格队列后被误以为不重要 | 在项目阶段转换和审批/递交接口实施对应阶段门禁，并显示时间线/逾期提醒 |
| 解析质量被降噪后被忽视 | 顶部摘要、`parse_exceptions_pending` 明确准入阻断原因、审计和 SLA |
| 双写期间新旧结果短暂差异 | 输出差异报表，不自动用新结果推进审批；完成对账后才灰度切换 |
| 规则分类存在业务歧义 | `unstructured`/`manual_review` 优先，不推断进入可计算项 |

本方案**不做**：自动投标、自动报价、模型自动确认低置信条款、模型自由选择人员、将向量相似度作为准入分数、把历史样本的项目—文件差异当作本轮缺陷修复。
