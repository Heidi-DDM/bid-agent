# 00-项目规则

> 项目：某建设集团「投标智能体」 ｜ 文档治理基线：v1.0 ｜ 建立日期：2026-08-25
> 本文件是项目协作的规则总纲，与 `AGENTS.md` 配套；`AGENTS.md` 面向 AI 代理与协作者，本文件记录完整规则与依据。

## 1. 项目定位与阶段

- 当前阶段：**产品与工程文档体系建立期（Iteration 0）**。不开发业务代码，不启动定时采集，先完成文档、决策记录、需求与迭代规划。
- 最终形态（规划）：公开招标情报收集 → 企业私有资料匹配 → 满分准入门禁 → 人工投标审批 的端到端系统。
- 本期目标：最小验证闭环（人工粘贴公告/上传招标文件 → 不可变原文 → 解析 → 资料匹配 → 满分准入 → 人工审批），见 `docs/02-迭代计划.md` 与 `docs/03-功能规格/F008`。

## 3. 架构与数据分层（三层分离 + 四层职责）

三层数据分离（既有资产，保留）：

```text
raw（公开原文）   —— 不可变，原始公告/招标文件，版本只增不覆盖
rules / schema    —— 规则与 Schema（schema/ 目录，已审计）
情报 / 交付物      —— 结构化情报、主卡/子卡、日报、推送（情报库/、data/）
```

四层职责（ADR-001 新增，本期核心）：

| 层 | 职责 | 是否允许判断 |
|---|---|---|
| 公开情报采集层 | 公告/文件采集、原文保存、事实结构化 | 否，只保留原文事实 |
| 企业私有资料层 | 资质、业绩、项目经理、证书等资料维护 | 否，只维护已验证资料 |
| 资格与资源匹配层 | 按规则逐项匹配、计分、识别缺项 | 是，但仅限可配置规则和证据化结果 |
| 投标审批层 | 决定是否实际投标 | 必须由企业负责人完成 |

## 4. 业务规则红线

1. **禁止编造**：缺失字段标"待补/待核实/不可判定"，禁止推断填充；企业资料不足时输出"不可判定/待补材料"，不得误判为满足或不满足。
2. **纯事实红线**：公开情报层禁止"值得投/有倾向/中标率"等分析断语（旧 PRD §四/§七、骨架树 §4.4）。
3. **满分 ≠ 自动投标**：满分仅进入 `pending_bid_approval`，最终批准由人完成；系统不自动代表公司作出法律或商业承诺。
4. **数据缺失默认阻断**：缺失关键证据 → `blocked_missing_data` / 待补队列，不推断满足。
5. **硬性缺项一票否决**：任一 `hard_requirement` 不满足/缺证据 → `blocked_hard_requirement` / `not_qualified`。
6. **公告版本不覆盖**：变更/澄清公告按 `project_id` 挂接历史；raw 原文不可覆盖。
7. **项目经理名录真实性**：不得生成不存在的项目经理或证书资料；无法核验的经理不计入"满分可投标"。
8. **匹配结论可溯源**：每条匹配结论回链招标条款（clause_ref）与企业证据（evidence_ref）。

## 5. 采集与合规（既有资产，保留）

- 采集模式：测试期 `manual_trigger`（手动/单条 URL），正式期才允许 `scheduled`；切换门槛：P0 验收（≥10 条真实公告人工验收）+ 法务《数据来源合规清单》签字（旧 PRD §5.4、§9.1）。
- 限频：单源 ≤1 次/5 分钟；全平台 ≤200 次/小时；测试期触发式同样遵守。
- robots：遵守 robots.txt，禁止路径不采集。
- UA：透明标识性 UA（含公司信息），不伪装。
- 不绕过技术保护、不抓取登录/付费/非公开内容；个人信息最小化、内部使用、30 天后脱敏。
- 数据源分级 L0/L1/L2/L3：L0 第三方授权 API、L1 官方平台、L2 地市自建、L3 禁止。
- 门禁：G0 采集 → G1 清洗 → G2 事实卡 → G3 情报库 → G4 推送 → G5 归档 → G6′ 校准（月度抽查 ≥100 条）。
- 去重：L1 精确 / L2 近似 / L3 合并；跨平台指纹去重；变更公告不覆盖历史。

## 6. Git 与仓库治理

- 仓库：本项目根目录 Git 仓库（2026-08-25 初始化，首次提交为文档体系）。
- **禁止提交**（.gitignore 已覆盖 + 人工确认）：

| 类别 | 示例 |
|---|---|
| 企业私有资料 | `企业资料台账20260821/`、各类清单 xlsx |
| 招标文件/原文 | 招标文件 docx/pdf、`raw/` 抓取原文、`scripts/*.html` 页面快照 |
| 密钥与凭据 | .env、API key、Cookie、证书私钥 |
| 运行数据与日志 | `data/`、`daily/`、`推送日志/`、`报告/`、`*.log` |
| 构建产物 | `node_modules/`、`ppt_build/`、`__pycache__/`、`*.pyc` |

- 提交前检查：`git status` 确认无敏感文件；误提交的敏感文件必须从历史中清除（改写历史需负责人确认）。
- 提交信息规范：`docs: 说明` / `feat: 说明` / `fix: 说明` / `refactor: 说明`，中文描述，聚焦"为什么"。

## 7. 术语速查

| 术语 | 定义 |
|---|---|
| 项目主卡 / 子卡 | 一项目一主卡 + 按事实类型拆分的子卡（basic/time/qualification/scoring/amount/compliance/requirement/checklist/advantage） |
| 事实卡 | 只记录公告原文可溯源事实，无分析断语 |
| advantage 子卡 | 企业私有库数据与招标要求匹配（旧 PRD 占位 → 本期正式启用为匹配矩阵） |
| G0-G6′ | 采集/清洗/事实卡/情报库/推送/归档/校准门禁 |
| L0-L3 | 数据源分级 |
| Material | 最小数据治理单元：公告、招标文件、企业资质、业绩、人员证照等 |
| 准入状态机 | draft→collecting→parsed→matching→blocked_missing_data→blocked_hard_requirement→not_qualified→qualified_full_score→pending_bid_approval→approved_for_bidding/rejected_by_approver→archived（见 ADR-001） |
