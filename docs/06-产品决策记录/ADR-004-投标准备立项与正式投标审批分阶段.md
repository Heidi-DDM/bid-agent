# ADR-004：投标准备立项与正式投标审批分阶段（P0 止血 + 分阶段工作流）

- **状态**：已接受（Accepted，Iteration 0 部分当日落地；Iteration 1+ 分批实施）
- **日期**：2026-09-16
- **决策人**：AI 产品经理/文档治理 Agent 起草；依据 `reports/2026-09-16-投标智能体完整优化方案.md`（两轮外部验收联合评审结论）；待公司经营负责人/投标业务负责人评审确认
- **关联**：ADR-001（投标准入边界）、ADR-002（RAG 边界）、ADR-003（采集边界）、`docs/03-功能规格/F008、F009、F010、F011、F020、F021、F022、F023、F024`、`docs/05-项目现状.md`

## 1. 背景与问题

两轮外部验收（2026-09-16 复盘）表明：现有系统更接近「招标文件解析 + 企业资料初步核对 + 人工复核队列 + 准入演示原型」，存在三个必须先关闭的 P0 问题：

| 编号 | 问题 | 业务后果 |
|---|---|---|
| P0-01 | worker 无进程级心跳、`/readyz` 不反映异步能力 | 异步采集/解析/匹配/重算无法证明闭环可用，前端「API 就绪」与「异步任务不可用」口径混为一谈 |
| P0-02 | 公告、招标文件、规则、匹配结果可能语义串档 | 后续所有匹配与审批可能建立在错误项目的材料上 |
| P0-03 | 已过投标截止的项目仍可重算并进入审批 | 对失效项目继续操作，形成严重业务误导 |

同时，现有流程把「是否值得投入编标资源」「解析是否正确」「资料是否齐全」「规则可否执行」「资源是否可用」「是否满足内部准入」「是否具备递交条件」七类性质不同的判断压在同一条直线上，导致早期审批被后期递交动作阻断、所有问题共用一个「补录证据」入口。

**处理方式**：按优化方案 §15 顺序执行——先登记本 ADR，再更新功能规格变更记录，再改实现与测试；不静默改写已冻结契约。

## 2. 决策内容

### 2.1 新增「投标准备立项」阶段，不替代正式投标审批

在「公告发现/快速预核」与「完整匹配」之间新增一道**人工管理门**：投标准备立项（preparation decision）。

- 负责人可选：启动投标准备 / 暂缓 / 放弃项目 / 转人工专项评估；
- 立项通过后允许：组织编标团队、完整研究招标文件、协调资源、进入全量匹配与审批准备；
- **立项通过不代表**：正式同意投标、同意报价、同意递交、同意对外承诺。

**边界（不可让步）**：新增立项不是取消「满分才进入正式投标审批」（ADR-001 §2.2）；它是一个更早、更轻量、仅代表投入编标准备资源的人工管理动作。`qualified_full_score → pending_bid_approval → 人工审批` 链路保持不变。

### 2.2 项目生命周期状态分阶段

在 ADR-001 状态机基础上扩充（完整定义见优化方案 §5.1，Implementation 按迭代落地）：

```text
discovered → selected → precheck_in_progress → preparation_pending
  → preparation_approved / preparation_declined
  → collecting → parsed → rule_review → matching → remediation
  → approval_ready → pending_bid_approval → bid_approved
  → submission_ready → submitted → opened → closed → archived
```

横切/异常状态作为独立的 `blocking_flags` 或版本状态，不用单一字符串表达：`stale`、`identity_conflict`、`overdue`、`cancelled`、`correcting`。

### 2.3 项目身份一致性硬校验（P0-02）

- 任何招标文件挂接、规则生成、正式匹配之前，系统按「多字段加权 + 关键字段硬冲突」计算项目身份：
  - 项目编号/采购编号/包号不一致 → **硬冲突**；
  - 采购人、项目名称指纹、地点显著不一致 → 高风险冲突；
  - 预算、截止时间差异 → 警告或硬冲突（依澄清/延期公告解释）；
  - 无法确认 → 进入人工核对，不允许直接匹配。
- 校验结果三态：`identity_confirmed` / `identity_warning` / `identity_conflict`；
- **门禁（Iteration 0 立即生效，服务端实现）**：`match`、`recalculate`、正式审批创建三个入口均须先自动执行或复用项目身份校验，再判定门禁；`identity_conflict` 必须在入口同步拒绝（HTTP 409）并留审计，worker 同时保留兜底校验；`identity_warning` 允许人工核对（Iteration 1 起禁止进入正式匹配）。

### 2.4 截止、过期与失效（P0-03）

- 项目同时记录截止日期 `bid_deadline` 与可获得时的精确截止时点 `bid_deadline_at`（带时区；统一按中国时区解释）。原文只给日期时不得虚构时分秒，`bid_deadline_at=null`，readiness 必须明确标为“日期级、时刻待补”。
- 有 `bid_deadline_at` 时，在该时点及之后立即判定过期；仅有 `bid_deadline` 时采用保守降级：截止当日不提前判过期，自次日零时起阻断。解析、人工登记和身份校验回写均保留来源审计。
- 截止已过：项目标记 `overdue`，禁止新建匹配/重算任务与正式审批，旧 MatchRun 不得作为当前准入结论（只允许查看历史与复盘）；
- 存在延期公告/澄清时，基于新版本重新确认截止日期/时点后方可恢复流程；
- 审批通过后发生文件、规则、证据或截止变更的，旧审批失效（Iteration 3 完整实现变更影响分析）。

### 2.5 结论语义与证据链最低要求

统一结论语义（对齐优化方案 §3.2）：`satisfied / not_satisfied / blocked_missing_data / manual_review / stale / overdue / cancelled / correcting`。其中：

- `blocked_missing_data` ≠ `not_satisfied`；`manual_review` ≠ `evidence_supplement`；
- **任何 `satisfied`（hard/scored）结论必须有可回链的企业证据引用**；证据不可定位时自动降级为 `manual_review`，不得计入正式准入（Iteration 0 立即生效，服务端实现）；
- 评分公式未结构化：得分为 `null`，显示「暂不可计算/需人工复核」，**不得写 0 分**，不得标满足；内部满分准入默认阻断。

### 2.6 异步任务可靠性（P0-01）

- worker 进程必须周期写心跳（含 runner 标识），`/readyz` 增加 worker 心跳检查，与数据库/对象存储/OCR/模型并列；
- 前端全局状态按「API / 数据库 / 异步 worker / 模型」拆分显示并说明影响范围（如「API 与数据库正常；异步任务不可用，历史结果可查看，新建采集/解析/匹配/重算暂不可用」）；
- 不以页面历史数据证明异步链路可用。

### 2.7 Iteration 1 最小闭环：快速预核、投标准备立项与任务中心

为避免把“是否投入编标准备资源”和“是否满足内部准入、是否实际投标”混为一谈，Iteration 1 引入以下独立对象与服务端门禁；详细 API/字段契约由 F020 v1.21 登记。

1. **快速预核（QuickPrescreenRun）**：由投标专员或经营负责人发起，仅读取项目身份、截止事实、文件/解析存在性及最近匹配的缺失/复核事实，生成不可变快照和审计。输出只能包含“已登记事实、待补、待核实、风险类型”，必须带“不是投标建议、不是正式匹配、不能替代正式审批”的提示；不得改变项目准入状态、不得创建正式审批、不得输出报价/中标概率/推荐投标结论。
2. **投标准备立项（PreparationRecord）**：状态仅为 `preparation_pending / preparation_approved / preparation_declined`。仅经营负责人可以创建、批准或拒绝；创建与决定均必须有理由/意见并审计。它仅表示允许投入编标、核验和资源协调工作，**不是**正式同意投标、报价、签章或递交；不得改变 `internal_admission_eligible`、不得绕过“满分才创建正式投标审批”。已过截止项目不得新建或批准准备立项。
3. **RemediationTask**：把问题分流为 `document_check / evidence_supplement / rule_review / resource_confirmation / identity_confirmation / termination_correction / stale_review`；每项保存来源项目/匹配运行/要求、责任角色/责任人、截止、证据要求、关闭条件、状态与完整审计。任务状态为 `open / in_progress / evidence_submitted / resolved_pending_recalculation / closed / rejected / cancelled / overdue`。资料补证仅可提交证据，不能自行宣称“满足”；规则、文件、资源、身份问题只能提交处理结论后等待重新核验/重算；明确 `not_satisfied` 的 `termination_correction` 禁止用补证动作关闭。自动任务以来源指纹幂等生成；只有新匹配结果已不再产生该来源问题，或符合专门关闭条件时，系统才可关闭。
4. **身份警告**：从 Iteration 1 起，`identity_warning` 与 `identity_conflict` 均阻断正式匹配/重算；前者只能由投标专员或经营负责人依据必填人工核对说明执行 `identity-confirm` 后解除，后者必须纠正双方事实后重新校验。快速预核和准备立项可如实展示/处理身份问题，但不能把警告默认为已确认。

前端仅负责展示阶段、下一责任角色和可执行动作；上述所有状态迁移、权限、截止和身份门禁必须由服务端再次校验。
