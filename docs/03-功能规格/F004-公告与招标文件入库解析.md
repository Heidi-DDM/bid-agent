# F004-公告与招标文件入库解析

- **需求来源**：R004、R005、R014、R015 ｜ **状态**：draft（Iteration 1/2 冻结）
- **关联**：ADR-001、F002、F003、F005、`raw/`、`scripts/`

## 1. 背景与目标

- **背景**：既有采集与发布层已实现公告采集/事实卡/日报（`scripts/`、`schema/` v0.3.x，manual_trigger）；新增需求要求能获取**招标文件**（不止公告）并入库解析，且测试期保持手动触发。
- **目标**：合规数据源 + 手动触发（人工粘贴公告 / 上传招标文件 / 单条 URL）→ 不可变原文入库 → 解析（主卡、资格要求、评分规则、时间线、废标条款）→ 字段级引用；测试期不启动 scheduled。

## 2. 非目标

- 7×24 全网监控、全平台自动抓取、自动定时采集（R015 后置）；
- 登录/付费/非公开内容抓取；绕过技术保护；任何非合规采集。

## 3. 用户角色与端到端步骤

| 角色 | 步骤 |
|---|---|
| 投标专员 | 粘贴合规公告 URL/正文、上传招标文件（docx/pdf）→ 查看解析结果 → 人工复核 |
| 数据管理员 | 维护数据源合规记录 |
| 法务 | 审核数据源清单 |

端到端步骤：手动触发 → 原文保存（不可变 raw + hash）→ 解析 → 主卡/子卡生成 → 字段级引用 → 人工复核/门禁通过 → 进入匹配（F008）。

## 4. 数据对象

### 4.1 公告/招标文件原文（raw）

| 字段 | key | 说明 |
|---|---|---|
| 原文ID | `raw_id` | 主键（如 zb-YYYYMMDD-NNN） |
| 类型 | `doc_type` | announcement / tender_document |
| 来源 | `source_links[]`、`source_platform` | 每链接可点击 |
| 原文内容 | `content` | 不可变 |
| 哈希 | `content_hash` | SHA-256 |
| 版本 | `version` | 不覆盖 |
| 采集模式 | `collect_mode` | manual_trigger（测试期）/ scheduled（正式期） |
| 解析状态 | `parse_status` | pending/parsed/partial/failed/manual_review |

### 4.2 解析产物

- 项目主卡（`T-CARD-*`）：字段见旧 PRD §6.1 + F005。
- 事实子卡：basic / time / qualification / scoring / amount / compliance / requirement / checklist（既有）+ advantage（正式启用，见 F005）。
- 字段级引用：`clause`（条款号）+ `source_link` + 原文摘录（逐字）。

## 5. 输入/输出与证据要求

- 输入：公告 URL/正文、招标文件 docx/pdf。
- 输出：raw 原文（不可变）+ 主卡 + 子卡 + 字段级引用。
- 证据要求：每个非空字段必须绑定来源链接与原文摘录；缺失标"待补"。

## 6. 业务规则

1. **测试期仅 manual_trigger**：人工粘贴/上传/单条 URL；scheduled 待 P0 验收（≥10 条真实公告）+ 法务《数据来源合规清单》签字后切换（旧 PRD §5.4）。
2. **采集红线**（既有，保留）：robots、限频（单源 ≤1 次/5 分钟、全平台 ≤200 次/小时）、透明 UA、不绕过技术保护、不抓登录/付费/非公开。
3. **公告版本不覆盖**：变更/澄清按 project_id 挂接；raw 不可覆盖。
4. **去重**：L1 精确 / L2 近似 / L3 合并（既有）。
5. 解析失败/部分解析 → 人工复核（manual_review），不得静默跳过，不得编造。
6. 门禁：G0-G4 沿用既有；解析产物须过 G2（事实卡门禁）。

## 7. 失败/空态/异常状态

| 状态 | 处置 |
|---|---|
| 解析失败（版式不支持、加密 PDF、图片型 PDF） | manual_review + 提示人工处理 |
| 部分解析 | 已解析字段保留并溯源，未解析字段标"待补" |
| 权限不足（上传者非数据管理员） | 拒绝 + 审计 |
| 原文哈希不一致 | 阻断 + 告警 |
| 截止时间已过 | 既有规则：不入日报、标注已截止（见 schema §10） |

## 8. API 目标态契约

```text
POST   /api/v1/intake/announcement        # 粘贴公告（URL 或正文）
POST   /api/v1/intake/tender-document     # 上传招标文件（multipart）
POST   /api/v1/intake/{raw_id}/reparse    # 重新解析（人工复核后）
GET    /api/v1/intake/{raw_id}            # 原文 + 解析产物 + 引用
POST   /api/v1/intake/{raw_id}/confirm    # 人工确认通过门禁
```

## 9. 权限、数据隔离、审计和合规

- 公开原文：public_read；上传动作记录审计。
- 招标文件若含企业私有信息（如标书），按 enterprise 密级处理（F003）。
- 个人信息：最小化、30 天后脱敏（既有红线 R4）。

## 10. 验收标准与测试计划

- 验收：①手动触发可入库一条真实公告/招标文件并生成主卡；②原文不可变（hash 校验）；③字段级引用齐全；④解析失败正确进入人工复核；⑤无 scheduled 采集。
- 测试计划：真实样例（康保储能EPC、广宗葫芦中学、阜平县高铁片区管网项目）试解析；限频/robots 校验；版本与去重用例。
