# F021-招标材料入库、解析与模型分析运行时

- **需求来源**：R021 ｜ **状态**：定稿草案 v1.7（2026-09-15）
- **关联**：F004、F005、F008、F017、F019、F020、F022、F025、ADR-001、ADR-002

## 1. 目标与试点范围

实现农大项目单条招标文件的真实处理：上传 → 原文固化 → 路由 → 文本/OCR 解析 → 条款抽取 → 主卡/子卡/规则草案 → L2 知识库索引 → 人工复核。测试期只允许 `manual_trigger`。

非目标：批量/定时采集、登录或付费内容、`.gef/.etb` 解密、自动报价、模型直接做准入判断。

## 2. 处理流水线

1. 接收文件或合规 URL，生成 Material 草稿。
2. 计算 SHA-256，写入不可变版本；原文失败则停止。
3. Document Router：PDF 文本检测 + 图片占比检测；DOCX 解包；图片型 PDF/图片进入 OCR。
4. 解析器输出页码、文本片段和候选字段；无法定位的字段为 `__待补__`。
5. 模型仅做条款分类、字段归一化和要求拆分，输出严格 JSON。
6. JSON Schema 校验：字段必须含 `clause`、`source_link`、`assertion`、`confidence`；不合格输出进入人工复核。
7. 投标专员确认后写入主卡、子卡和 RuleSet 草案，项目状态进入 `parsed`；编排器随后自动创建一次匹配任务，项目状态进入 `matching`。解析页不要求、也不允许投标专员选择企业资料或手动触发首次匹配。
8. 解析片段进入 F025 的 L2 索引；索引失败不影响原文保存，但必须进入 `manual_review`/`retryable`，不得伪造“已建立知识库”。

### 2.1 解析结果聚合与分组展示（v1.3 / 09-优化方案 §3.3）

解析完成不直接跳转“人工补录”：增加“解析结果”视图（`prototype/requirements.html`），按业务语言分组呈现，接口：

**`GET /api/v1/parse/projects/{project_id}/requirements`** —— 解析结果聚合（写规则集前=parse_candidates 视图；确认后=Requirement 视图）：

```json
{ "request_id": "r-…", "project_id": "PJ-…", "source": "candidates|confirmed",
  "groups": [ { "group": "资格与资质", "group_label": "资格与资质",
      "items": [ { "id": "RC-…", "title": "建筑工程施工总承包资质等级",
          "requirement_type": "hard", "value": "建筑工程施工总承包二级及以上",
          "assertion": "须具备…（原文摘录）", "clause_ref": "招标公告 §3.2",
          "page_no": 5, "confidence": "high",
          "review_status": "pending", "issue": null,
          "source_link": null, "audit": { "material_id": "MAT-…", "content_hash": "9c42…" } } ] } ] }
```

- 分组固定六类：项目基本信息 / 资格与资质 / 项目经理与人员 / 业绩、财务与信用 / 场地、设备与其他资源 / 投标动作与风险条款；分组判定由候选 `category`/`req_type` 确定性映射，不可判定 → 归“其他”并如实标注，禁止推断。
- `title` 为可读标题（由条款/类别确定性生成，标注“待复核”）；`value` 为要求值（编辑后确认时以 revised 值为准）；`issue` 记录缺失/歧义原因（未识别/条款冲突/扫描不清等，无则 null）。
- 内部 `requirement_id`（候选 ID）、`material_id`、hash 仅出现在 `audit` 折叠字段，不作为主展示。
- 复核动作（`POST /parse/candidates/{candidate_id}/review`，v1.3 业务语义对齐）：`approved`=确认无误；`revised`=编辑后确认（必带 `revised_payload`，如修正后的 assertion/value）；`rejected`=标记无法确认（**必带结构化原因**：扫描不清 / 条款冲突 / 未识别 / 需业务解释，写入 `review_note`，原因枚举前端选择，这不是上传企业材料）。决策仍由投标专员执行，原因与备注全部审计留痕。

**v1.5 复核语义补充（missing 候选三选一 + 逐字校验）**——针对 `missing_marker=true`（锚点未命中、`assertion=__待补__`）的候选：

| 决策 | 语义 | 契约 |
|---|---|---|
| `not_applicable`（新增） | **确认本文件无此条款**（如本文件资格审查不要求财务审计报告） | 仅 missing 候选允许；必带 `review_note`（人工核查说明）。确认写入时不产出 Requirement，但写入 `RuleSet.snapshot.not_applicable[]`（anchor_key/category/reviewer/note），审计可查“谁确认了本文件没有这一条”。 |
| `revised` | **人工定位补录**：人在原文中找到了该条款 | `revised_payload` 必含 `assertion`（原文逐字摘录）与 `page_no`（整数），可含 `clause_ref`。后端逐字校验：去空白后 `assertion` 必须是该页原文子串，否则 400 invalid_request（禁止编造）；扫描件/OCR 路由无法校验时放行并在 payload 标 `verbatim_check=skipped_ocr`。通过后 `missing_marker=false`、`confidence=low`、`rule.located_by=human`。 |
| `rejected` | 仍无法确认（扫描不清等） | 原因枚举不变。 |
| `approved` | **禁止**（400 `invalid_request`） | 通过一条“未定位到原文”的候选没有业务含义；v1.4 及以前确认写入时被静默跳过，等于规则无声消失，v1.5 起显式拒绝。 |

对非 missing 的规则候选，`revised` 的 `revised_payload.assertion` 同样须通过逐字校验，修正说明写 `review_note`（v1.4 前端把说明文字直接写进 assertion 属实现偏差，v1.5 纠正）。主卡/条款字段候选（`main_card_field`/`term_field`）的 `revised` 只改 `value`，不做逐字校验。

**v1.6 补充（2026-09-15）**：
- **逐字校验归一**：判定“是否逐字”时对两侧做 NFKC + 去不可见字符 + 去空白的归一比对（容忍全角/半角数字、PDF 阅读器复制的编码变体）；用户粘贴中单独成行的页码（跨页复制页脚伪影）剥除后再比对；填写页码命中不了时在**全文**定位真实所在页（印刷页码与物理页序可能不一致），落库以校验出的真实页为准。归一仅用于判定与页码定位，不改动落库摘录；编造文本仍被拒绝。
- **rejected（无法确认）可重开**：它是“暂未核实”的搁置而非终局判断——复核人找到原文/辨清扫描件后可改判（approved/revised/not_applicable），原决策保留在 audit_events。其余终态（approved/not_applicable）不变。
- **确认后编排以规则集为准**：规则集写入即触发索引与首次匹配；存在“无法确认”驳回时材料停在 manual_review 不再阻断匹配（匹配的是已确认要求；驳回项跟进另行处理）。索引允许 manual_review 材料；L1 公告原文（净化 txt，无扩展名对象）路由支持纯文本。

**v1.5 定位展示**：missing 候选的 `clause_ref` 输出 `null`（不再回传锚点基线文件的条款提示——它在别的招标文件里是错误位置），改为 `locate_hints[]`（该锚点的检索关键词，供人工全文搜索）；所有候选的 `source_link` 为原文文件接口 `GET /api/v1/materials/{material_id}/file?version=N`（Bearer 鉴权、按 permission_scope 过滤；前端以 blob 打开并附 `#page=<page_no>`）。`audit` 内的 `requirement_id`/`kind`/`content_hash` 属系统追溯编号，前端须配白话说明且不得作为定位手段展示。

### 2.2 复核与补录分流（v1.3 / 09-优化方案 §3.4）

- 复核队列（parse_candidates）只处理“系统从招标文件读到了什么”：通过/编辑后通过/无法确认+原因，不含材料上传动作。
- 材料补录队列（`GET /projects/{id}/queues` 的 blocked_missing_data）只在**匹配完成**后生成，每项绑定 requirement_id/条款/缺失字段/原因/用途/建议材料类型/负责角色/截止，前端可跳转预填补录表单（契约见 F020 §2.2.5 v1.7）。
- 低置信、冲突、缺页、必填字段缺失的候选才进入复核队列；高置信且规则完整候选可批量通过（保留抽样复核与审计）；界面不得用“N 项”总数替代待办说明。
- **v1.5 页面阶段门控**（`prototype/queue.html`）：规则集未确认 → 只显示「解析候选复核」区；确认写入并存在匹配结果后 → 才显示「处置队列」与「补录企业证据材料」区（后者默认折叠，从队列项带入上下文时展开）。术语拆分：复核阶段对 missing 候选的动作叫**人工定位条款**（对象是招标文件条款），匹配后的动作叫**补录企业证据材料**（对象是企业证据），不再共用“补录”。
- **v1.7 批量通过工具栏两页同源**：「批量通过（高/中置信且已定位）」由 `prototype/review.js` 的 `mountBatchToolbar` 提供，解析结果页（requirements.html）与复核页（queue.html ① 区）**都必须**挂载——2026-09-15 上午把「去人工复核」主入口改到复核页后，用户在复核页找不到批量按钮（此前只做在解析结果页）。可批量范围不变：`review_status=pending` 且已定位到原文且高/中置信且非旧版遗留；未定位/低置信/需重新决策项仍逐条处理。工具栏仅投标专员、复核阶段（规则集未确认且有候选）显示。

### 2.3 确认写入的判定时点 `as_of`（v1.5）

`POST /parse/projects/{project_id}/materials/{material_id}/confirm` 写入 RuleSet/Requirement 时每条要求必须固化 `as_of`（F008 §4.1：判定时点不得默认当前时间）。取值链：

1. `body.as_of`（投标专员在确认框中确认或改写，ISO 日期 `YYYY-MM-DD`）；
2. 该材料已 `approved/revised` 的主卡字段 `deadline_bid`（投标文件递交截止时间）的日期部分——这是 F008 定义的 `bid_deadline`；
3. 项目既有规则集的 `as_of` 锚点（澄清版本重确认时沿用）；
4. 以上皆无 → 400 `invalid_request`，提示先确认「投标文件递交截止时间」字段或在确认框填写。

响应携带 `as_of_source`（`body` / `main_card:deadline_bid` / `rule_set_anchor`）；聚合接口 candidates 视图返回 `as_of_suggestion {as_of, source, page_no}`，前端确认框**必须展示 as_of 与来源**并允许改写，改写值与来源写入审计 basis。

DeepSeek API 仅可接收经权限检查的 `public_read` 文本；企业资料不得作为提示词、上下文、日志或调试样本发送到外部模型。模型输出必须经过 Schema 校验和人工/规则核验后才能写入结构化对象。

### 2.4 P4-2 条款发现（v1.6，2026-09-15）

确定性锚点按固定关键词匹配，版式/措辞超出锚点词面时命不中——但条款在原文中明确存在（实测：联合体协议分工、联合体资质认定、质量保证金预留比例等）。处理方式：**引入大模型做“定位”而非“判断”**（P4 方法论延伸）：

- worker 解析链在锚点抽取与 P4 兜底之后调用 `llm_fallback.discover_rule_candidates`：模型从相关页（按类别关键词选页）输出**候选条款的原文逐字摘录**；
- 校验链与 P4 相同：quote 须为某页归一后精确子串；**与既有候选归一摘录互为子串（短边 ≥16 字）或命中任一锚点模式的丢弃**（发现只补盲区，不重复既有覆盖）；类别须命中封闭词表（资质/人员/业绩/财务/信用/评分/动作），判不出丢弃；每份文件最多 8 条；
- 通过者产出 **generic 候选**（`rule={"type":"generic","located_by":"llm","discovered":true}`，requirement_id 含摘录内容哈希 → 重解析幂等；category 决定六组归属，标题带「大模型发现，待复核」），`confidence=low`、note 明示须人工核对——与所有候选同走 approved/revised/rejected，模型永不直接产生规则；
- 开关（`LLM_FALLBACK_ENABLED`）关闭 / 非 public_read / 网络失败 → 零副作用。发现候选中混入模板占位条款（如「金额：/」）属预期噪音，由人工复核裁决。

## 3. 模型适配器契约

输入：页码化文本、候选章节、项目 ID、原文哈希。输出：`field_key`、`value`、`clause`、`assertion`、`confidence`、`requirement_type`、`review_reason`。

模型调用必须记录模型名、版本、提示模板版本、输入哈希、输出哈希和耗时；不记录完整原文。模型不可输出“值得投”“中标率”“自动报价”等字段。模型不可替代确定性规则引擎对 `satisfied/not_satisfied/unverifiable` 的判定，也不得生成企业事实或投标结论。

## 4. 农大抽取清单

- 主卡：项目名称、编号、招标人、代理机构、地区、项目类型、限价、保证金、投标截止、开标时间、来源链接。
- 资格：12 条 hard requirement，含资质、安许、项目经理、社保、安全员、技术团队、财务、信用、联合体、响应性、保证金、限价。
- 评分：技术/商务/信用结构，主观项标记 `subjective`，类似业绩拆成投标人和项目经理两条客观项。
- 动作：报名/文件获取、保证金、递交、开标四阶段。
- 澄清：两份澄清作为同一 project_id 的新 Material 版本；影响要求时使旧 RuleSet `stale`。

## 5. 失败处置

解析失败、客观评分项疑似漏项、字段无引用、模型输出不符合 Schema、澄清冲突、哈希异常均进入 `manual_review` 或阻断；不得静默跳过或用模型补写事实。

## 6. 验收与测试

- 农大招标 PDF 可生成完整 Material 和可人工复核的主卡/子卡。
- 20 条规则草案与 `golden_requirements_nongda.json` 对齐，声明/执行数量可核对。
- 随机抽取字段可从结果回跳原文页码和条款；缺失字段显示待补。
- 文本 PDF、扫描 PDF、DOCX、损坏 PDF、`.gef` 各有路由测试。
- 关闭模型服务时仍能入库和进入人工复核；不得假装模型成功。
- 解析完成事件必须幂等：同一 `project_id + tender_material_version + ruleset_version` 只发布一个 `parse.completed` 和一个首次匹配任务；重复轮询或刷新不得重复触发。
- L2 条款黄金集 `Recall@5 >= 0.90`，每条召回结果可回跳 Material/版本/哈希/页码；模型关闭时原文入库仍可用，解析与索引失败进入可解释复核队列。
