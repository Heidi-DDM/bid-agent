# F001-文档与工程治理

- **需求来源**：R001 ｜ **状态**：定稿（Iteration 0 交付）
- **关联**：ADR-001、`docs/00-项目规则.md`、`docs/01-需求池.md`、`docs/02-迭代计划.md`、`docs/04-修改日志.md`、`docs/05-项目现状.md`

## 1. 背景与目标

- **背景**：项目此前只有旧 PRD 与复用方案，无文档治理体系，无 Git 仓库；新增"满分准入门禁"范围变化需要显式登记（ADR-001），后续迭代需要单一事实源。
- **目标**：建立文档体系与协作规则，使字段、状态机、API、规则变更可追溯、可评审；敏感资产（企业资料/招标文件/原文/密钥/日志/构建产物）不入库。

## 2. 非目标

- 不开发业务代码；不引入文档生成工具；不迁移旧 PRD 内容。

## 3. 用户角色与端到端步骤

| 角色 | 职责 |
|---|---|
| 产品经理/知识工程师 | 维护 docs/ 体系、ADR、规格 |
| 投标专员 | 评审需求池、规格、原型（验收方） |
| 经营负责人 | 评审 ADR、审批契约（验收方） |
| 法务 | 评审合规条款（文档层面） |
| 开发/测试 | 以规格为单一事实源实现与验收 |

端到端步骤：变更需求 → 登记需求池/ADR → 更新规格与变更记录 → 评审 → 冻结 → 实现 → 回填修改日志。

## 4. 数据对象

- 文档对象：`docs/` 下的规格与记录，Markdown 为主。
- 唯一 ID：需求编号 Rxxx；规格编号 Fxxx；ADR 编号 ADR-xxx；迭代编号 Iteration N。
- 状态：planned / in_progress / done / blocked / backlog（需求）；draft / review / frozen（规格与契约）。

## 5. 输入/输出与证据要求

- 输入：业务变更、用户反馈、评审意见。
- 输出：需求池条目、规格、ADR、修改日志。
- 证据要求：每个决策/变更须有"谁、何时、为何"记录；ADR 须附影响评估与替代方案。

## 6. 业务规则

1. 单一事实源：字段 key、状态机、API 契约以 docs/03 为准。
2. 变更必登记：所有变更写入 `docs/04-修改日志.md`。
3. 不静默修改旧 PRD：范围变化走 ADR。
4. 冻结契约的修改需评审（Iteration 3 冻结后）。

## 7. 失败/空态/异常状态

- 文档漂移（规格与实现不一致）：修改日志 + 评审标记。
- 空态：新需求未关联规格时标注"待关联规格"。

## 8. API 目标态契约

- 无对外 API；文档变更采用文件级版本控制（Git）。

## 9. 权限、数据隔离、审计和合规

- Git 白名单见 `.gitignore`；敏感资产一律不提交。
- 审计：修改日志 + Git 历史。

## 10. 验收标准与测试计划

- 验收：①docs/ 目录齐全；②ADR-001 存在且覆盖范围变化；③Git 可提交且无敏感文件。
- 测试计划：提交前 `git status` 检查 + 敏感关键词扫描（如 `token`/`cookie`/企业目录名）。

## 11. 影响范围

- 全项目协作方式；不直接影响业务数据。

## 12. 回链

- 旧 PRD §一（同步更新约定）；复用方案 §七（工程约束）；ADR-001。
