# F026：搜索预筛、待选池、规则配置与管理面板

- **状态**：冻结
- **版本**：v1.0（2026-09-21）
- **关联**：ADR-005、F020、F022、F023、F024

## 1. 范围

本规格新增搜索后的确定性预筛、统一待选池、规则配置、企业资料复核重匹配与经营负责人管理面板。它不改变 ADR-001 的四层边界：公开层不作商业判断，系统不自动投标/报价。

## 2. 预筛与搜索简报

### 2.1 输入与输出

预筛输入限于列表页可证实的 `title`、`source_name`、`source_url`、`publish_date`、公告类型和规则配置。输出为：

- `screen_state`：`brief` / `needs_manual_review` / `excluded_non_tender`；
- `matched_industries[]`、`matched_exclusions[]`、`announcement_type`、`rule_version`；
- `missing_fields[]` 与原始候选事实。

只有标题明确属于中标/成交公示、采购结果、采购/询价/磋商、招租/租赁/资产处置或其他非招标类型时，才可为 `excluded_non_tender`。未知行业、地区、规模不得自动删除，必须为 `needs_manual_review`。

### 2.1.1 大模型辅助预筛（第二层，ADR-006）

对第一层未判定或仅规则命中的条目，由大模型按标题 + **企业业务画像**（`rules.business_profile`，经营负责人可配置，留空用内置施工企业默认）做**受约束的事实性分类**：

- 输出契约：`category`（封闭词表）、`relevant`（yes/no/uncertain——以"该企业会不会投这个标"为口径，不是"是不是招标机会"）、`reason`（必须为标题子串，机器校验）、`confidence`（high/medium/low）；
- 判定落位：`relevant=yes` → `pending`（**主列表"可选深入"**，可直接选择深入）；`relevant=no` 且置信度 ≥ 中 → `expired` + `excluded_by="llm"` 留审计，**人工可恢复**（与业务无关的专业设备/IT/办公/服务采购也在此列）；uncertain / 低置信 → `needs_manual_review`（**单独"待人工确认"页签**，不进主列表）；
- 待选池主列表只呈现"可选深入"条目——搜索→入池→两层筛选后，用户直接在主列表选择深入；
- **永不输出商业投标建议**；开关关闭/门禁不过/网络失败/校验不过 → 零副作用回落人工（fail-open）；已有 `llm_assist` 的条目幂等跳过；画像/提示词变更后经回填脚本 `--reset` 全量重判。

### 2.2 简报

简报供投标专员选择是否深入，必须显示事实来源与规则命中，禁止出现“值得投”“推荐投标”“中标率”等措辞。进入深入链路的动作是人工 `select_deep_dive`，随后仍须抓取详情、上传完整招标文件、解析确认和匹配门禁。

**交互口径（v1.2，2026-09-22 晚 ADR-006）**：搜索页只负责触发搜索并展示「增量简报收口」，**不展示任何候选列表**（含只读诊断视图，已移除）；待选池是唯一筛选工作台：两层预筛（确定性规则 + AI 分类）自动分流，待处理内 AI 相关机会优先排序、公告要点可折叠展开（快速否决在池内完成）、展示投标截止（仅建档后有值）。「选择深入」为一键漏斗（标记 + 抓取建档），须**内联二次确认**（防误触发）。统一漏斗术语：**入池 → 选择深入 → 抓取建档 → 上传招标文件 → 进入匹配**。

## 3. 待选池

| 字段 | 说明 |
|---|---|
| `candidate_id` | 对应不可变搜索候选 |
| `project_key` | 仅用于同项目候选归并，不改写标题 |
| `pool_status` | `pending` / `needs_manual_review` / `deep_dive` / `dismissed` / `superseded` / `expired` |
| `screening` | 规则版本、确定性命中与预筛状态 |
| `first_seen_at` / `last_seen_at` | 首次/最近搜索发现时间 |
| `dismissed_by` / `dismissed_reason` | 软删除的责任与原因 |
| `replaced_by_candidate_id` | 更新替换链 |

每次搜索成功落库后都同步待选池。相同 `project_key` 的新候选只可替换仍为 `pending` / `needs_manual_review` 的旧候选；`deep_dive`、`dismissed`、`imported` 均不可自动覆盖。删除只软删除待选状态，不删除公告候选、原文或审计记录。

## 4. 筛选/排除规则

规则由经营负责人创建新版本并启用，内容包括 `industry_keywords`、`exclude_keywords` 和启停项。规则读接口对两类角色开放，写接口仅经营负责人开放。每一条简报绑定执行时的规则版本；规则更新不回写历史筛选结论。

## 5. 角色与复核

| 能力 | 投标专员（含 Agent） | 经营负责人 |
|---|---:|---:|
| 搜索、简报、待选池、选择深入 | 是 | 是 |
| 企业资料录入、证据核验、解析复核、匹配重算 | 是 | 是 |
| 规则配置、管理进度面板 | 否 | 是 |
| 最终投标审批、豁免 | 否 | 是 |

补录企业资料后必须经核验。`verify-and-recalculate` 仅以已核验证据版本为输入，为指定且已有匹配结果的项目创建新的重算任务；旧准入结果标为 `stale`，并记录审计。

## 6. 管理面板与建议口径

经营负责人可读取：项目总数、各状态数量、待筛选/已深入数量、未关闭处置任务、按当前状态聚合的阻塞项目。面板不暴露企业资料明细。

匹配建议字段仅使用下列可执行下一步：`补齐并核验证据`、`核对硬性条件原文或企业事实`、`人工复核`、`提交经营负责人审批`、`等待解析/匹配任务完成`、`无自动动作`。每项须给出状态或条款/证据引用；不得输出商业投标建议。

## 7. API 契约

- `GET /api/v1/discovery/pool`：待选池简报，支持 `status`、`limit`、`offset`、`sort`（`publish_date` 默认：发布时间优先、缺日期沉底；`last_seen`：最近发现）。
- `GET /api/v1/discovery/briefing`：最近一次（或 `job_id` 指定）搜索的入池增量摘要（新增/待处理/需人工确认/自动排除/被替换 + 规则版本），只统计事实。
- `POST /api/v1/discovery/candidates/{candidate_id}/select`：人工选择深入。
- `POST /api/v1/discovery/candidates/{candidate_id}/dismiss`：软删除，正文可含 `reason`。
- `POST /api/v1/discovery/candidates/dismiss-batch`：批量软删除（逐条走单条状态机，已深入不可删；统一原因，一次审计汇总）。
- `POST /api/v1/discovery/candidates/{candidate_id}/restore`：恢复 AI 预筛排除的候选（仅 `excluded_by=llm`；确定性排除与人工删除不可由此恢复）。
- `GET|PUT /api/v1/discovery/rules`：预筛规则读取/版本化更新。
- `POST /api/v1/discovery/rules/preview`：规则试跑——按提交配置回放最近 N 条候选（默认 200，上限 500），返回状态分布与样例；不落库、不切换生效版本。
- `GET /api/v1/manager/dashboard`：经营负责人进度面板。
- `POST /api/v1/enterprise/verify-and-recalculate`：资料核验后按证据版本重匹配。

待选池条目附带 `candidate.deadline_bid`（投标截止，仅建档后有值）与 `candidate.highlights`（公告要点：资质/金额/采购人/代理/工期/开标地点/联合体/质量），均来自 `detail_summary` 非缺失值，缺失为 `null` 不推断。

## 8. 验收

1. 中标/成交/采购结果类公告不进入默认搜索简报；未知条目不误删。
2. 一次搜索的候选进入待选池；后续同项目新候选仅替换未处理旧项，人工选择与删除可审计。
3. 规则更新产生新版本，旧简报保留旧版本。
4. 文件解析确认后，前端能正确读取解析候选、确认规则并显示匹配任务/错误，不以假成功替代后端状态。
5. 两级角色权限符合表 5；经营负责人可看面板与审批，投标专员不可改规则或审批。
6. 补证未核验时不触发“满足”；核验后重算产生新 run 且旧结果过期。
