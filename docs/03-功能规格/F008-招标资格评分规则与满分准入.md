# F008-招标资格评分规则与满分准入

- **需求来源**：R008、R009 ｜ **状态**：定稿 v2.0（2026-09-29 用户五项业务裁定：判定口径以招标文件「资格审查资料清单」实打实要求的提交材料为准）
- **关联**：ADR-001、ADR-004、ADR-007、ADR-008、F003、F005、F006、F007、F009、docs/12

## 1. 背景、目标与边界

- **背景**：招标文件中的资格、响应性、评分和投标动作要求，须与企业私有资料逐项匹配，并以企业内部“满分准入”政策决定是否送人工审批。
- **目标**：产出可追溯、可复算的规则化核查结果，识别缺证据、硬性不满足、待人工复核和可进入审批的项目。
- **边界**：系统不作法律资格结论、不预测中标、不自动报价或投标。`qualification_result` 仅表示“按已配置招标条款和已核验证据的规则化核查结果”；最终投标决定始终由人作出。

## 2. 四类独立结论

不得以单个布尔值混淆资格、得分、动作和内部决策；每次匹配必须同时输出下列结果：

| 结论 | key | 内容 | 不代表 |
|---|---|---|---|
| 资格/响应性核查 | `qualification_result` | 必要资格、资质、人员、业绩、信用、联合体、格式性否决等是否按规则满足 | 法律意见或最终资格审查结果 |
| 当前评分结果 | `scoring_result` | 可计算客观项得分、待输入报价、待人工评审项、分数差距与评分公式版本 | 评标委员会最终得分或中标概率 |
| 投标准备度 | `operational_readiness` | 各阶段动作、责任人、截止时间和回执是否就绪 | 已递交或已开标，除非有对应回执 |
| 内部准入 | `internal_admission_result` | 企业内部“满分准入”政策是否允许送人工审批 | 自动投标或商业承诺 |

`qualified_full_score` 是内部“满分准入政策已满足”的状态名称，不得展示为“评标满分”或“必然中标”。

## 3. 用户角色与端到端步骤

| 角色 | 步骤 |
|---|---|
| 投标专员 | 确认条款、标段和澄清版本 → 选择企业资料/候选经理 → 录入经授权的报价输入 → 复核矩阵和诊断清单 |
| 数据管理员 | 补充、核验、更新证据及有效期 |
| 技术/投标评审人 | 对技术方案等主观项完成内部质量评审并留痕 |
| 经营负责人 | 查看内部准入结论，决定审批、驳回或依法授权的豁免 |

流程：锁定招标文件及澄清版本 → 拆分要求 → 自动读取截至 `as_of` 的有效企业资料并执行一次匹配 → 分别计算四类结论 → 输出全部诊断 → 满足内部政策时进入 `pending_bid_approval`。补录核验后才允许引用新证据快照重算；前端结果查看不触发匹配。

## 4. 数据对象

### 4.1 Requirement：三类要求与通用字段

| 类型 | key | 范围 | 基本判定 |
|---|---|---|---|
| 硬性要求 | `hard_requirement` | 资格、资质、人员、业绩、财务、信用、联合体、资格预审/后审、否决投标条款 | 不满足或无法核验不得视为资格/响应性通过 |
| 计分要求 | `scored_requirement` | 商务、技术、资信、报价等评分细则 | 按可复算公式或人工评审状态输出评分结果 |
| 动作要求 | `action_requirement` | 报名、CA、保证金、文件编制/递交、开标等 | 仅按该动作要求的阶段判断是否就绪或已完成 |

每个 Requirement 均须保存如下字段：

| 字段 | key | 必填 | 说明 |
|---|---|:--:|---|
| 要求 ID | `requirement_id` | 是 | 规则实例主键 |
| 类型、分类 | `req_type` / `category` | 是 | 分类须与原条款一致 |
| 标段 | `lot_id` | 否 | 未分标段填 `null`；分标段项目不得跨标段混用证据/评分 |
| 条款与原文 | `clause_ref` / `assertion` | 是 | 逐字摘录，回链 F005 溯源 |
| 规则表达式 | `rule` | 是 | 结构化条件，见本节后文 |
| 证据要求 | `evidence_required[]` | 是 | 证据类型、份数、时点、是否可复用 |
| 判定时点 | `as_of` | 是 | `bid_deadline`、资格预审截止、动作截止或明确日期；不得默认使用当前时间。解析确认写入规则集时默认取该招标文件已人工确认的主卡字段 `deadline_bid`（取值链见 F021 §2.3），投标专员可在确认框改写，改写留痕 |
| 缺失处置 | `missing_action` | 是 | 仅允许 `blocked_missing_data` / `manual_review`，并在规则快照中固化 |
| 失败后果 | `failure_effect` | hard 必填 | `not_qualified` / `blocked_hard_requirement`；不得由实现推断 |
| 规则优先级 | `priority` | 是 | 澄清或补遗覆盖后的生效顺序 |
| 替代/逻辑组 | `logic_group` / `operator` | 是 | `all` / `any` / `at_least_n`；支持“资质 A 或 B”等原文逻辑 |
| 联合体角色 | `consortium_role` | 否 | `none` / `leader` / `member`；联合体允许时必须逐成员核查 |

`rule` 至少支持类型/等级、数量、年限、金额、规模、专业、地区、单位、最小/最大值、时间窗口、`all/any/at_least_n`、替代项和证据复用标记。规则不得用自然语言隐含 AND/OR、单位换算或“近三年”等时间口径。

### 4.2 计分项专属字段

| 字段 | key | 必填 | 说明 |
|---|---|:--:|---|
| 满分与权重 | `max_score` / `weight` | 是 | 非负数；总分、分组小计和权重须可复算 |
| 评分性质 | `score_nature` | 是 | `objective` / `subjective` |
| 公式 | `score_formula` | objective 是 | 参数、取整/四舍五入、封顶、扣分、最低线和分组关系；引用原评分细则 |
| 评分输入 | `score_inputs[]` | 按需 | 例如经授权录入的投标报价；必须标注来源、录入人、时间和版本 |
| 复用/去重规则 | `reuse_policy` | 是 | 同一业绩、人员或证书是否可重复计分 |
| 主观内部评审 | `internal_review` | subjective 是 | 评审人、依据、意见、时间、复核人、状态；不是评标委员会打分 |

- `objective` 仅在公式、所需输入和证据均齐全时自动计算。报价分必须有人工录入的 `quoted_price`，系统不得生成、推荐或假定报价。
- `subjective` 仅输出“待内部质量评审/已通过/未通过”；不得把内部评审结果写成评标委员会分数。未完成内部评审时，`scoring_result` 为 `manual_review`。
- 存在技术标最低得分线、报价异常、暗标格式等淘汰条件时，须分别建为 `hard_requirement` 或评分规则中的明确门槛，禁止隐藏在备注中。

### 4.3 动作项专属字段与时序

| 字段 | key | 必填 | 说明 |
|---|---|:--:|---|
| 要求阶段 | `required_by_stage` | 是 | `approval_ready` / `submission_ready` / `submitted` / `opened` |
| 动作状态 | `action_status` | 是 | `not_started` / `ready` / `completed` / `overdue` / `not_applicable` |
| 截止时间 | `deadline_at` | 是 | 含时区；来源为招标条款或澄清 |
| 责任人和回执 | `owner` / `receipt_evidence_refs[]` | 是 | 已完成必须有可核验回执 |

进入审批只检查 `required_by_stage=approval_ready` 的动作是否 `ready` 或 `completed`。递交、开标等后续动作不得作为进入审批的前置条件；到相应阶段时再检查 `submission_ready`、`submitted`、`opened`。

### 4.4 MatchMatrix

| 字段 | key | 说明 |
|---|---|---|
| 矩阵 ID / 项目 / 标段 | `matrix_id` / `project_id` / `lot_id` | 关联项目、标段和规则版本 |
| 要求与证据 | `requirement_id` / `tender_clause_ref` / `evidence_refs[]` | 每条结论必回链条款和企业证据 |
| 匹配结果 | `match_result` | `satisfied` / `partial` / `not_satisfied` / `unverifiable` / `manual_review` |
| 分数 | `score` / `max_score` | 仅计分项使用；不可计算时 `score=null`，不得填 0 分冒充计算结果 |
| 时点与版本 | `evaluated_at` / `as_of` / `rule_set_id` / `source_version_refs[]` | 用于重放与澄清追溯 |
| 缺口与理由 | `missing_items[]` / `match_reason` | 机器可读判定链：表达式、输入、证据、计算结果和原因 |

结果口径：`satisfied` 为证据充分且满足；`partial` 为部分量化条件满足，硬性项不可据此通过；`not_satisfied` 为证据充分但不满足；`unverifiable` 为缺证据或无法核验；`manual_review` 为解析不完整、规则无法执行或须人工判断。所有 `manual_review` 都必须带 `review_reason`。

### 4.5 RuleSet 与招标文件版本

`RuleSet` 须包含 `rule_set_id`、语义化 `version`、`effective_from`、`created_by`、完整 `snapshot`、变更 diff 及审批/发布记录。快照必须同时固化：Requirement、公式、默认缺失处置、准入政策、单位/取整规则和证据有效性规则。

招标文件、答疑、补遗或澄清产生影响要求/评分/时限的版本时，必须建立新的 `source_version_refs[]` 与 RuleSet 版本，标记旧矩阵和准入结果为 `stale`，重新核查后才可进入审批。历史项目保留其当时版本，不被覆盖。

### 4.6 AdmissionResult

| 字段 | key | 说明 |
|---|---|---|
| 判定与规则版本 | `admission_id` / `project_id` / `lot_id` / `rule_set_id` | 主键与可回放版本 |
| 四类结论 | `qualification_result` / `scoring_result` / `operational_readiness` / `internal_admission_result` | 均为结构化对象，不用单一布尔替代 |
| 内部准入布尔 | `internal_admission_eligible` | 仅代表是否可送人工审批 |
| 可计算分数 | `total_score` / `max_total_score` / `score_gap_items[]` | 不含尚不可计算或主观实际评标分 |
| 阻断/待补/复核 | `blocked_items[]` / `pending_items[]` / `review_items[]` | 每项须含状态、后果、责任人、截止时间和证据要求 |
| 项目经理 | `manager_matches[]` | 主推荐/备选、时点可用性和 F007 硬条件结果 |
| 解释与新鲜度 | `explanation[]` / `result_freshness` | `current` / `stale`；每步可追溯 |

### 4.7 工作域字段与细粒度结论（v1.9 / ADR-008，2026-09-28 冻结目标契约）

单一字典 `runtime/core/domain_dict.py`（DICT_VERSION=adr008-v1.0.0）为唯一版本源，服务端拥有判定，前端不猜测：

1. **Requirement 域字段**：`domain`（qualification/scoring/operation，由 req_type 确定性映射）、`decision_scope`（admission/information_only，仅前者进入内部准入）、`score_classification`（objective_calculable/subjective_review/price_formula/methodology_only/unstructured）、`comparison_status`、`person_binding_policy`（none/same_person_required/same_team_required/alternative_candidates_allowed）、`role_code`/`role_count`（project_manager/construction_lead/design_lead/tech_lead/safety_officer/technical_team）、`task_kind`（registration/ca_cert/bond/preparation/submission/opening/site_visit/other）。
2. **细粒度结论与原因码**（match_items 事实层：`reason_code`/`required_value`/`observed_value`/`evidence_state`/`candidate_plan_id`/`person_id`/`next_action`）：`not_satisfied`（verified_quantity_insufficient/grade_below_requirement/certificate_expired/profession_mismatch/onsite_conflict——处置是更换/补足资源，不得以补证明掩盖）；`blocked_missing_data`（enterprise_record_missing=台账 0 条/evidence_missing/evidence_pending_verification/validity_date_missing）；`manual_review`（evidence_conflict/rule_unstructured/candidate_plan_unselected/professional_judgement_required）；`not_calculable`（formula_missing/authorized_input_missing/scoring_evidence_missing，仅评分域）；`parse_exception`（anchor_not_located/llm_candidate_pending/source_conflict）。**历史 unverifiable 行无 reason_code 时投影为 legacy_ambiguous（「历史结果，需重算确认」）**，禁止 unverifiable 作为前端唯一显示词。
3. **候选班子（candidate_plans 三表）**：人员相关 satisfied 必须回链同一 `person_id` 与 `candidate_plan_id`；无完整方案时输出 `manual_review/candidate_plan_unselected`，不得跨人拼接；排序只用确定性优先级（证据完整度/证书等级/person_id），不用模型偏好或向量相似度。
4. **评分分类**：`methodology_only`（评标方法说明）仅归档、不计入 total/max；无可自动计算项时 objective_score/objective_max=null+calculable=false，不显示 0/0 或「未满分」；`price_formula` 无授权输入 → not_calculable，系统绝不推荐报价。
5. **动作分层**：action_requirement 结论=动作状态（not_started/ready/completed/overdue/not_applicable），只产出 operation_tasks；除显式 `required_by_stage=approval_ready` 外不参与审批门禁、不进缺证队列。
6. **准入公式 v2（docs/12 §4.4）**：`internal_admission_eligible = 资格(硬性 admission 域全 satisfied) ∧ 评分(可计算项满分+主观已过评审) ∧ 解析质量(blocking parse_exceptions=0) ∧ 审批前动作(approval_ready 项 ready/completed) ∧ run.is_current ∧ 非历史样本上下文`；阻断原因用稳定枚举 `blocking_reasons[]`（qualification_not_satisfied/scoring_not_ready/parse_exceptions_pending/approval_actions_not_ready/historical_sample_context/result_stale）。

## 5. 证据有效性

证据在 `as_of` 时点同时满足以下条件才可用于“满足”：文件存在且 hash 一致、来源/持有人明确、在有效期内、已由责任人核验、符合条款规定的原件/签章/份数/主体要求，并能回链到具体条款。业绩、社保、信用查询、财务报告等须按条款的起算期和截止日验证，不能只以当前日期判断。证据变更、到期、撤销或原文版本变化后，关联结果自动标 `stale` 并重新计算。

## 6. 业务规则

### 6.1 四类结论的计算

```text
qualification_result =
  all(hard_requirement.match_result == satisfied)

operational_readiness.approval_ready =
  all(action.required_by_stage == approval_ready
      => action.status in [ready, completed])

internal_admission_eligible =
  qualification_result.status == passed
  AND scoring_result.internal_full_score_ready == true
  AND operational_readiness.approval_ready == true
  AND exists(qualified_available_project_manager)
  AND all(required_evidence is valid_at_as_of)
  AND result_freshness == current
```

`scoring_result.internal_full_score_ready` 是企业内部政策：全部可计算客观项达到其 `max_score`，且每个主观项已通过内部质量评审；它不是评标委员会实际满分。若报价、技术方案或其他输入尚未形成，评分结果必须标为 `not_calculable` 或 `manual_review`，内部准入不通过但不改变资格结论。

### 6.2 统一状态处置

| 情形 | 匹配结果/准入状态 | 处置 |
|---|---|---|
| 证据充分，资格性硬项不满足 | `not_satisfied` / `not_qualified` | 不得进入审批 |
| 证据充分，响应性硬项（如已逾期、保证金方式不符）不满足 | `not_satisfied` / `blocked_hard_requirement` | 不得进入审批 |
| 关键证据缺失或无法核验 | `unverifiable` / `blocked_missing_data` | 待补，不得推断不合格或满足 |
| 解析漏项、澄清冲突、规则无法执行或需专业判断 | `manual_review` | 人工复核，不参与自动准入 |
| 量化项部分满足 | `partial` | 硬性项不通过；计分项按明确公式计算，否则人工复核 |
| 全部内部政策条件满足 | `internal_admission_eligible=true` → `qualified_full_score` → `pending_bid_approval` | 仅送人工审批 |

### 6.3 执行模式、解释与重新计算

- **门禁模式**在出现首个足以阻止审批的状态后停止状态迁移；**诊断模式**仍继续检查可独立判断的要求，输出全部缺口。两种模式必须标明执行范围，不得把未执行项目显示为通过。
- 每条 `explanation` 至少包含：Requirement、条款版本、表达式、`as_of`、输入值、证据、计算/判断结果和执行人或系统版本。
- 人工修正条款分类、公式、主观内部评审、报价输入和证据核验都必须审计；影响结果的修改须重新计算，并在已进入审批时撤回至匹配状态。
- 人工豁免遵循 F009：不改变资格结论、评分事实或“满分”定义，只能在授权范围内让审批人看到被豁免的阻断项。

### 6.4 门禁衔接

G3.5 只判断是否可进入人工审批，不阻断公开情报推送 G4。资格/评分/准备度任一结果为 `manual_review`、`not_calculable`、`stale` 或存在阻断项时，不得自动前进到 `pending_bid_approval`。

## 7. API 目标态契约

```text
GET    /api/v1/projects/{id}/requirements
POST   /api/v1/projects/{id}/requirements          # 人工修正，留痕
POST   /api/v1/projects/{id}/rule-sets              # 依据招标文件/澄清创建快照
POST   /api/v1/projects/{id}/match                  # 供解析完成事件/重算流程调用，支持 gate / diagnostic；不作为前端首次匹配按钮
GET    /api/v1/projects/{id}/matrix
GET    /api/v1/projects/{id}/admission              # 四类结论 + 全部诊断
POST   /api/v1/projects/{id}/score-inputs           # 仅录入人工授权输入，不生成报价
POST   /api/v1/projects/{id}/recalculate            # 补录核验后按新证据版本重算
```

## 8. 权限、审计与合规

- 匹配矩阵及报价输入均为 `restricted`；审批层按 F003/F009 权限查看。
- 规则发布、证据核验、人工复核、评分输入、内部质量评审、动作完成和重新计算均须记录人、时间、依据、前后值和版本。
- 个人信息按 F003/F007 最小化展示；系统不把内部评审结论写入公开情报层。

## 9. 验收标准与测试计划

- 验收：①四类结论独立输出；②资格、缺证据、人工复核状态按 §6.2 唯一映射；③ AND/OR、标段、联合体、时间/单位、澄清覆盖可重放；④客观公式、报价输入、取整/封顶和去重可复算；⑤主观项仅为内部评审、不冒充评标得分；⑥动作按阶段而非“递交/开标已完成”进入审批；⑦门禁与诊断模式结果一致且范围清晰；⑧证据或澄清变更使旧结果失效并重新计算。
- 测试集：至少 10 个真实脱敏工程项目，覆盖资格预审/后审、分标段、联合体、价格公式、技术最低分、保证金、澄清覆盖、证据过期、报价未输入、无合格经理和审批撤回；人工确认每个黄金样本的条款拆分与预期结果。
- 执行清单：R009 的验证待办、角色、证据留痕和退出条件见 `docs/验证/R009-匹配引擎与黄金样本验证清单.md`；完成前不得以演练输出代替验收。

### 9.1 可执行一致性与回归门禁（2026-08-27 新增）

- **唯一可执行规则源**：每个黄金样本的 Requirement 必须由受 Git 管理的结构化文件提供；不得在报告、演练脚本和规则配置中分别手工维护条款编号或数量。博野五标段当前基线为 `scripts/matching/golden_requirements.json`，16 条（hard 9 / scored 3 / action 4）。
- **覆盖门禁**：每次运行必须输出 `declared`、`executed`、`complete`；诊断模式仅当 `executed == declared` 才可称为“全量匹配”。门禁模式短路时必须标识未执行项，禁止将其展示为通过。**v1.6 运行口径**：一次 gate 运行 = 先 diagnostic 全量执行 + 再 gate 计算业务状态（F023 §2 第 4 步）：矩阵/处置队列取全量，短路后条目逐条 `gate_executed=false` 并在 `coverage.short_circuited[]` 点名；结果页对未执行项显式 `not_evaluated`，禁止默认 `unverifiable` 冒充“已判定缺证”。
- **未结构化规则门禁（v1.6）**：规则仅定位到条款原文、未结构化出可比对参数（资质类别/等级、经理专业/等级/B证/在建、业绩起算期/规模/类型、保证金金额/形式、限价金额、技术团队专业、安全员人数等）时，引擎一律 `manual_review` 并写明缺什么，**不得判 `not_satisfied`（编造失败）也不得在空约束上判 `satisfied`（虚假通过）**。安全生产许可证为独立证据种类 `safety_license`（不分等级，存在时点有效且已核验的许可证即满足）；联合体按极性字段 `accepts_consortium` 判定（接受 → 无额外阻断；极性未判定 → manual_review）。
- **时点门禁**：证据只有在 `verified_at <= as_of`、签发/生效日不晚于 `as_of`、有效期覆盖 `as_of` 且状态为已核验有效时，才可以产生 `satisfied`。任一字段缺失或不满足时点要求一律 `unverifiable`，不得以今日核验结果回填历史项目。
- **字段执行门禁**：验收测试必须对财务年度/替代材料、信用三查、项目经理专业等级+B证+在建状态、保证金金额/形式、报价人工输入和响应性证据分别设负例；规则字段存在但未参与判定视为验收失败。
- **回归门禁**：合入前必须运行 `python -m unittest discover -s scripts/tests -v` 和 `python scripts/matching/run_golden_lab.py`。依赖由根目录 `requirements-dev.txt` 声明，GitHub Actions 同步执行；任一失败不得把“演练跑通”写入需求池或项目现状。
- **报告口径门禁**：报告中的 Requirement ID、条款数、版本、执行结果必须从同一次运行的结构化输出生成或逐项比对；历史 `scripts/parse_lab/r008/`、`r009/` 是探索性材料，不再作为 F008 验收依据。
