# F008-招标资格评分规则与满分准入

- **需求来源**：R008、R009 ｜ **状态**：draft（Iteration 2/3 冻结）
- **关联**：ADR-001（满分定义）、F003（证据）、F005（主卡/子卡）、F006（资质业绩）、F007（项目经理）、F009（审批）

## 1. 背景与目标

- **背景**：新增业务要求第 1/2 条：招标资格、人员、业绩、资信及评分要求须与公司私有资料逐项匹配打分；只有"满分且无硬性缺项"才能进入待投标审批。
- **目标**：将招标文件要求拆为三类（hard/scored/action），定义可配置、可解释的准入公式与"满分"判定，产出字段可溯源的匹配矩阵与准入结果。

## 2. 非目标

- 不自动投标、不自动报价、不预测中标概率；不以"模型认为适合"代替规则与证据；不把资料不足默认为满分。

## 3. 用户角色与端到端步骤

| 角色 | 步骤 |
|---|---|
| 投标专员 | 确认解析出的三类要求 → 配置评分项（如有缺项）→ 选择资料与候选经理 → 复核匹配矩阵 |
| 数据管理员 | 补证据/核验资料 |
| 经营负责人 | 查看满分评分面板与阻断项 |

端到端步骤：解析要求 → 分类（hard/scored/action）→ 资料匹配 → 计分 → 满分判定 → 阻断（待补/待核实）或进入待投标审批（F009）。

## 4. 数据对象

### 4.1 三类要求（Requirement）

| 类型 | key | 内容 | 判定 |
|---|---|---|---|
| 硬性要求 | `hard_requirement` | 资格、资质、人员、业绩、信用、保证金、截止时间、联合体等 | 任一关键项不满足/缺证据 → 阻断 |
| 计分要求 | `scored_requirement` | 商务、技术、资信等可配置评分项 | 每项定义满分值、匹配证据、缺失处置 |

计分项按性质分两类（F005 §4.2.1 契约）：

- **objective 客观项**：自动计分，纳入满分判定（`score == max_score`）；证据缺失 → 待补/待核实；
- **subjective 主观项**：系统不自动计分，输出"待人工评审判定"，由评审/经营负责人判定后回填（manual_verified，留痕）；未判定前该项目不满足"满分"条件。
| 动作要求 | `action_requirement` | 报名、CA、保证金、递交、开标 | 未完成前不能进入审批 |

### 4.2 匹配矩阵（MatchMatrix）

| 字段 | key | 说明 |
|---|---|---|
| 矩阵ID | `matrix_id` | 主键，关联 project_id + 规则版本 |
| 要求引用 | `tender_clause_ref` | 回链招标条款（F005 子卡） |
| 企业证据引用 | `evidence_refs` | 回链 F006/F007 证据 |
| 匹配结果 | `match_result` | satisfied / partial / not_satisfied / unverifiable |
| 计分 | `score` / `max_score` | 计分项 |
| 缺失项 | `missing_items[]` | 待补/待核实清单 |

### 4.3 规则版本（RuleSet）

- `rule_set_id`、`version`、生效日期、创建人；历史项目保留当时规则版本快照。

## 5. 输入/输出与证据要求

- 输入：F005 解析产物（三类要求）、F006 资质业绩、F007 项目经理。
- 输出：匹配矩阵 + 满分判定 + 阻断/待补清单。
- 证据要求：每条匹配结论必须回链招标条款（tender_clause_ref）与企业证据（evidence_refs）；无证据不判"满足"。

## 6. 业务规则

### 6.1 准入公式（可配置且可解释）

```text
eligible_for_approval =
  all(hard_requirements == satisfied)
  AND all(scored_requirements.score == scored_requirements.max_score)
  AND all(action_requirements.status in [ready, completed])
  AND exists(qualified_available_project_manager)
  AND all(required_evidence is valid)
```

### 6.2 "满分"的显式定义

1. 所有必填硬条件满足（hard_requirement.satisfied）；
2. 所有客观评分项得满分（objective score == max_score），且所有主观评分项已人工判定通过（manual_verified，留痕）；
3. 所有关键证据有效且未过期（required_evidence valid）；
4. 至少一名可用项目经理满足招标要求（F007 硬条件验证通过）；
5. 动作要求就绪/完成（action_requirement ∈ [ready, completed]）。

### 6.3 判定与处置规则

- **配置项如何定义"满分"**：每个 scored_requirement 必须配置 max_score（≥0）、匹配证据要求、缺失处置（按 0 分/进入人工复核/阻断，Iteration 3 与经营部确认默认值）；并按 F005 §4.2.1 标注 score_nature（objective/subjective）。
- **客观项自动计分**：objective 项由系统按规则与证据自动计分，证据缺失 → unverifiable → 待补/待核实，不推断满足。
- **主观项人工判定**：subjective 项系统不自动计分，交评审/经营负责人人工判定（manual_verified，留痕）；未判定前该项目不满足满分条件，阻断进入审批。
- **解析不完整**：评分项因招标文件无法完整解析（含客观项漏项）→ 进入**人工复核**（manual_review），不参与自动满分判定。
- **资料不足不能默认满分**：缺失 → unverifiable → blocked_missing_data / 待补队列。
- **评分结果只允许进入 pending_bid_approval**，不能自动投标。
- **结果展示**：总分、满分差距（差几分/差哪些项）、阻断项、待补项、招标条款引用、企业证据引用、项目经理匹配结果（主推荐/备选）。
- **规则版本化**：历史项目保留当时规则版本；规则变更须审计。

### 6.4 门禁衔接

- 准入判定作为 G3 之后的独立门禁（G3.5 匹配门禁，命名 Iteration 1 定稿）；通过 → qualified_full_score → pending_bid_approval。

## 7. 失败/空态/异常状态

| 状态 | 处置 |
|---|---|
| 硬性缺项 | blocked_hard_requirement / not_qualified |
| 证据缺失 | blocked_missing_data / 待补队列 |
| 解析不完整 | 人工复核 |
| 资料库为空 | 不可判定 / 待补材料 |
| 无合格项目经理 | 阻断并提示（可等待可用日期或调整候选） |
| 规则版本冲突 | 以 project 创建时规则版本为准 |

## 8. API 目标态契约

```text
GET    /api/v1/projects/{id}/requirements        # 三类要求列表
POST   /api/v1/projects/{id}/requirements        # 人工修正要求（留痕）
POST   /api/v1/projects/{id}/match               # 触发匹配
GET    /api/v1/projects/{id}/matrix              # 匹配矩阵
GET    /api/v1/projects/{id}/admission           # 满分判定 + 阻断/待补
GET    /api/v1/rule-sets/{id}                    # 规则版本详情
POST   /api/v1/rule-sets                        # 新建规则版本
```

## 9. 权限、数据隔离、审计和合规

- 匹配矩阵 restricted（含企业私有资料引用）；审批层可看全部。
- 规则版本变更审计（谁/何时/改了什么）；个人数据最小化（经理明细脱敏）。

## 10. 验收标准与测试计划

- 验收：①三类要求拆分规则可配置；②准入公式可解释执行；③满分判定与 ADR-001 §2.3 一致；④缺失不默认满分；⑤规则版本化生效；⑥结果展示字段齐全。
- 测试计划：公式全真/全假用例；硬性一票否决用例；证据过期用例；解析不完整→人工复核用例；无项目经理用例；规则版本回溯用例。
