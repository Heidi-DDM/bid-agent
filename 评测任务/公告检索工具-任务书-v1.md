# 招标公告检索工具 · 开发任务书

> **任务性质**：AI 辅助开发能力实测。本任务书自足完备，不依赖任何内部系统与既有代码，请从零搭建。技术栈不限，以第七节验收标准为唯一评判依据。
> **发布**：2026-09-11 ｜ **版本**：v1.0 ｜ **预期工作量**：4–8 小时（建议 1–2 个工作日内交付）

---

## 一、背景与需求目标

建筑施工企业的经营团队需要持续关注河北省内新发布的招标公告。目前公开公告分散在多个政府/国企交易平台，人工逐个翻看效率低、易遗漏。

**目标**：开发一个可本地运行的小工具——用户输入关键词，工具实时从指定平台抓取公告列表，返回结构化的匹配结果，并在一个简单网页上展示，每条结果可点击回看原文。

**范围一句话**：只做「关键词搜索 + 结果展示」，不做公告详情解析、不做数据入库与定时采集、不做推送通知。

## 二、信息来源（圈定，不得自行扩展）

以下三个平台是本任务唯一许可的数据来源。页面结构、分页方式、是否提供站内检索**均未告知**，需自行探测（见第六节阶段 1）。**禁止**使用任何第三方招标数据聚合服务或 API（如千里马、剑鱼标讯、采招网等）——数据必须来自下列平台的真实页面。

| # | 平台 | 入口地址 | 要求 |
|---|---|---|---|
| S1 | 惠招标（河北交投电子招标投标交易平台）· 工程类 | `https://ebidding.hebtig.com/jyxx/001001/001001001/trade.html` | 必做 |
| S2 | 河北省公共资源交易服务平台 · 交易信息 | `https://www.hbggzyfwpt.cn/jyxx/index` | 必做 |
| S3 | 邯郸市公共资源交易中心 · 工程建设招标公告 | `https://ggzy.hd.gov.cn/jydt/003002/003002001/trading_hall.html` | 选做（加分） |

2. 入口地址即公告列表页/频道页。列表页之外的页面（公告详情页）本任务不需要抓取，只需保留其链接。

## 三、功能需求

### 3.1 搜索

- 用户输入一个关键词串；多个词以空格分隔，**须全部命中**才算匹配（AND 关系）。
- 匹配对象为**公告标题**，按子串命中即可；大小写、全角/半角是否归一由实现者决定，但实际行为须与自测报告的描述一致。
- 空关键词视为无效输入：给出明确提示，或返回各源最新公告前 10 条（二选一，README 写明）。

### 3.2 结果字段（每条公告）

| 字段 | 要求 |
|---|---|
| `title` 标题 | 必有，来自列表页原文 |
| `url` 详情链接 | 必有，绝对地址，浏览器可直接打开 |
| `publish_date` 发布日期 | 有则输出 `YYYY-MM-DD`；**列表页解析不出 → `null`**，禁止从其他信息推断 |
| `source` 来源平台 | 平台名称 |

### 3.3 每源采集摘要（每次搜索结果必须附带）

| 字段 | 要求 |
|---|---|
| 平台 | — |
| 状态 | success / failed / skipped |
| 抓取条数 / 命中条数 | 本源实际抓到的公告总数、其中命中关键词的数量 |
| 失败原因（如有） | 超时 / 页面结构变化 / 被拒绝等，一句话即可 |
| robots 预检 | 检查时间 + 结论 |

### 3.4 展示页面

- 一个网页：关键词输入框、搜索按钮、结果列表（含 3.2 全部字段，标题可点击跳转原文）、各源采集摘要。
- 静态页面即可，不要求任何前端框架。

### 3.5 接口与响应

- 至少一个 HTTP 接口：入参关键词，出参结果列表 + 每源摘要（JSON）。
- 接口路径与后端框架不限。若单次搜索耗时可能超过 30 秒，须提供进度反馈机制（轮询或流式任选）；确定 30 秒内返回的可以同步。

### 3.6 失败处理

- 单源失败不得影响其他源；失败源在摘要中如实展示原因。
- 任何情况下不得以「空结果」冒充「失败」：空结果只能意味着确实无匹配。

## 四、数据真实性红线（违反任意一条 = 任务不通过）

1. **缺失不编造**：任何字段解析不出必须为 `null` 或「待补」，禁止用推断、猜测、默认值填充。
2. **结果必须真实**：所有结果须为验收当日平台真实存在的公告——链接可打开、标题与原站一致、日期与列表页一致（或为 null）。
3. **禁止伪造**：不得硬编码示例数据、不得用缓存的历史结果冒充实时采集、不得人工编辑数据文件充当采集输出。

## 五、采集行为约束

1. **robots 预检留痕**：每次搜索前对源域名做 robots.txt 检查并记录（时间 + 结论）。robots 是否允许**不作为阻断条件**，但必须留痕可查（日志或摘要均可）。
2. **限频**：对同一平台的连续请求间隔 ≥ 3 秒；单次搜索对单平台抓取列表页 ≤ 3 页。
3. **不绕过技术保护**：遇到验证码、登录要求或明确的反爬拦截时，停止该源采集并在摘要中如实标注；禁止破解验证码、伪造登录态、规避反爬机制。

## 七、验收标准

验收由评测方现场执行，**关键词现场指定**（含 1 个宽泛词、1–2 个窄词、1 个负例词），不接受预先录制的演示。

### 7.1 功能验收（逐项判定通过/不通过）

| # | 项目 | 标准 |
|---|---|---|
| A1 | 一键启动 | 按 README 指令在本机（macOS 或 Linux）一次启动成功；不依赖任何付费云服务 |
| A2 | 宽泛关键词 | 现场给定宽泛词（如「施工」），S1、S2 均正常返回，合计命中 ≥ 5 条；若当日平台公告量异常偏少，以评测方用同一关键词在平台页面肉眼核对的结果为准 |
| A3 | 窄关键词 | 现场给定窄词，允许 0 命中，但摘要须展示该源实际抓取条数，可佐证「确实无匹配」 |
| A4 | 负例关键词 | 输入不可能出现的词（如「量子纠缠」），返回 0 条且各源状态正常，不报错不崩溃 |
| A5 | 抽检真实性 | 从结果中随机抽 5 条：链接逐一点开可访问，标题与原站一致，日期与列表页一致（或为 null） |
| A6 | 日期提取率 | 结果页或自测报告如实展示各源发布日期解析率（0% 也可以，但数字必须与实测一致） |
| A7 | 故障演示 | 评测方将某一源地址临时改为不可达 URL，重跑搜索：其他源正常返回，该源状态 failed 并展示原因 |
| A8 | 采集留痕 | 代码与日志审查：robots 预检记录、请求间隔、单源页数上限三项均有实现 |

### 7.2 红线验收（一票否决）

见第四节。A5 抽检中任何一条对不上即触发；代码审查发现绕过技术保护的实现亦触发。

### 7.3 加分项

- S3 邯郸源接入并通过与 S1/S2 相同的 A2–A5 验收；
- 关键词全角/半角、首尾与多余空格的输入归一处理；
- 基本自动化测试（如解析器对保存的页面快照跑断言）。

## 九、交付物

1. **可运行代码仓库**：含 README（环境要求、一键启动命令、接口说明、已知问题）。
2. **自测报告**：自选 2 个关键词的各源返回条数、日期提取率、遇到的问题与处理方式。
3. **探测记录**：每源页面结构结论（条目位置、日期形态、分页方式）。

## 十、明确不做（防止范围蔓延）

- 公告详情页内容解析、招标文件下载；
- 数据库持久化（内存返回即可；做了不加分不减分）；
- 定时采集、变更监控、推送通知；
- 用户系统、权限、多租户；
- 对圈定三源之外任何平台的数据获取。
